15 ภาพรวม REST API

ภาพรวม

Vigil Platform เปิดให้ใช้งาน REST API ครบชุดสำหรับ operators, integrators และแอป Vigil Mobile เพื่อดึงข้อมูลเหตุการณ์ ค้นหา ตั้งค่ากฎแจ้งเตือน จัดการรายงาน และตรวจสอบสถานะระบบ — ทั้งหมดผ่าน HTTPS ที่ต้องผ่านการยืนยันตัวตน

  • Protocol: HTTPS REST (JSON request/response)
  • Realtime: WebSocket ต่อเดียวต่อ tab — push เหตุการณ์ใหม่โดยไม่ต้อง refresh
  • Auth: JWT-based, 3 วิธี (ดูหัวข้อถัดไป)
  • ทุก endpoint ที่ไม่ใช่ public ต้องผ่าน session ที่ valid

การยืนยันตัวตน (Authentication)

ระบบรองรับ 3 วิธีในการส่ง token — ทุกคำขอ API ตรวจสอบตามลำดับนี้:

วิธี รูปแบบ ใช้เมื่อ
Cookie (httpOnly) ตั้งอัตโนมัติเมื่อ login ผ่านเบราว์เซอร์ Dashboard มาตรฐาน — แนะนำสำหรับเบราว์เซอร์
Bearer Token Authorization: Bearer <token> API client, mobile app, third-party integration
URL Token ?token=<token> ลิงก์รายงาน PDF/PNG ที่ต้องการ auth โดยไม่มี header

Role สิทธิ์
admin เข้าถึงได้ทั้งหมด — อ่าน เขียน ลบ จัดการผู้ใช้ ตั้งค่าระบบ
viewer อ่านอย่างเดียว — ดูเหตุการณ์ สถิติ แผนที่ กล้อง
auditor อ่าน + export รายงาน — ไม่สามารถเปลี่ยนการตั้งค่า
public ไม่ต้อง login — เฉพาะ endpoint ที่กำหนด (branding, health ping)

WebSocket — Real-time Push

ทุก session ที่ login แล้วสามารถเปิด WebSocket connection เพื่อรับเหตุการณ์ใหม่แบบ real-time โดยไม่ต้อง reload หน้า

การยืนยันตัวตน (ตอน HTTP upgrade)

ตรวจสิทธิ์ตั้งแต่จังหวะ HTTP upgrade ไม่ใช่หลังต่อสำเร็จ — ไม่มี token ที่ใช้ได้ = ถูกปฏิเสธด้วย 401 ตั้งแต่ยังไม่เป็น WebSocket แหล่งของ token มีสองทางเหมือนฝั่ง REST API คือ cookie ชื่อ session (ส่งเองอัตโนมัติเมื่อ upgrade แบบ same-origin) หรือ query param ?token= (ทางสำรองสำหรับ Safari ITP)

wss://<host>/ws              # ใช้ session cookie
wss://<host>/ws?token=<token> # ทางสำรอง (Safari ITP)

สิทธิ์ระดับ Site และ View ถูกอ่านครั้งเดียว ณ ตอนต่อ — ถ้า admin แก้สิทธิ์ระหว่างที่ผู้ใช้เปิดจอค้างอยู่ จะมีผลเมื่อ reconnect

การขอรับหัวข้อ (subscribe)

ค่าเริ่มต้นของทุก connection คือ "ยังไม่ขอ stream หนัก" หน้าที่ต้องใช้ข้อมูลเต็มต้องส่ง frame นี้เข้ามาเอง หัวข้อที่ขอได้มี lpr และ face เท่านั้น (นอกเหนือจากนี้ถูกเมินเงียบ ๆ)

{"type":"subscribe","topics":["lpr","face"]}

ประเภทข้อความที่รับได้

ประเภท เนื้อหา
new_event เหตุการณ์ใหม่จากกล้อง — ID ชนิด กล้อง เวลา มีรูปหรือไม่
new_face ใบหน้าที่จับได้ใหม่ (Face Capture)
event_snapshot รูป snapshot ของเหตุการณ์มาถึงทีหลัง — หน้าจอเอาไปเติมรูปให้แถวที่แสดงอยู่แล้ว
clip_done media-recorder บันทึกคลิปเสร็จแล้ว
occupancy_update จำนวนคน/รถในพื้นที่เปลี่ยน (occupancy สดของจอ Live)
camera_status สถานะกล้องเปลี่ยน online/offline — ส่งเป็นชุด changes ทุก 30 วินาทีเมื่อมีการเปลี่ยน (ส่งถึงทุก socket ไม่ผ่านตัวกรอง topic)

ข้อความรุ่นย่อ (lite)

ข้อความ "หัวข้อหนัก" (anprAlarm ของ new_event และ new_face) ถูกยิงถี่มาก — วัดจริงราว 10 + 3.4 ข้อความ/วินาที ถ้าส่งเต็มทุกใบให้ทุกแท็บที่เปิดค้าง จะกินระดับหลายร้อย KB ต่อ 10 วินาทีต่อแท็บ แท็บที่ ไม่ได้ subscribe หัวข้อนั้นจึงได้ข้อความรุ่นย่อแทน (ไม่ใช่ "ไม่ได้รับเลย" เพราะตัวนับ badge และ toast ของทุกหน้ายังต้องขยับตาม) รุ่นย่อมีธง lite: true และเหลือเฉพาะ field ที่จำเป็น ขนาดราว 200–300 ไบต์ต่อใบ

{"type":"new_event","lite":true,"event":{ "id":…, "camera_id":…, "event_type":…, "event_time":…, "raw_json":{ "plate":… } }}

ข้อควรทราบ

WebSocket ต้องมี session ที่ valid เสมอ — ถ้า session หมดอายุ connection จะถูกตัดและ dashboard จะแสดง toast "session expired" แล้ว redirect ไป login

ผู้ใช้ที่ ไม่ใช่ admin จะได้ข้อความรุ่นที่ปิดบัง IP / MAC ของกล้องใน raw_json.rawXml แล้ว (v1.5.4 — ปิดช่องข้อมูลแผนผังเครือข่ายภายใน) รุ่นย่อไม่ได้รับผลกระทบเพราะไม่มี rawXml ติดมาอยู่แล้ว

รูปแบบ Response

สำเร็จ

HTTP 200 OK
Content-Type: application/json

// รายการ (list)
[{ "id": 1, "event_type": "Motion", ... }, ...]

// รายการเดียว หรือ action result
{ "id": 1, "enabled": true, ... }
{ "ok": true }

Error

HTTP 4xx / 5xx
{ "error": "คำอธิบายข้อผิดพลาด" }
HTTP Status ความหมาย
400ข้อมูลที่ส่งมาไม่ถูกต้อง (validation error)
401ไม่มีหรือ session หมดอายุ → ต้อง login ใหม่
403มี session แต่สิทธิ์ไม่พอ (เช่น viewer พยายามแก้ไข)
404ไม่พบ resource ที่ขอ
503Service ภายในไม่พร้อม (เช่น report-worker ยังไม่ start)

Pagination

Endpoint ที่คืนรายการจำนวนมาก (events, appearances, alert-logs) รองรับ query params ดังนี้:

GET /api/events?limit=50&offset=0&sort=desc
GET /api/appearances/search?limit=20&offset=0
  • limit — จำนวนรายการต่อหน้า (ค่าเริ่มต้นต่างกันตาม endpoint)
  • offset — ตำแหน่งเริ่มต้น (0 = หน้าแรก)
  • จำนวนรวมมาทาง response header X-Total-Count สำหรับคำนวณจำนวนหน้า

เพดานการนับ (count cap)

บนตาราง events ที่มีหลายสิบล้านแถว การนับให้ครบจริงแพงกว่าการดึงรายการที่จะแสดงเสียอีก /api/events จึงหยุดนับที่ 10,000 (ปรับด้วย EVENTS_COUNT_CAP) และ /api/appearances/search ใช้เพดานเดียวกัน (APP_COUNT_CAP)

  • ถ้าชนเพดาน จะมี header X-Total-Capped: 1 ติดมาด้วย และ X-Total-Count จะเท่ากับเพดานพอดี
  • หน้าจอเห็น header ตัวนี้แล้วแสดงผลเป็น "10,000+" แทนตัวเลขตรง ๆ — ไม่ใช่บอกว่ามีแค่หนึ่งหมื่นแถว
X-Total-Count: 10000
X-Total-Capped: 1

ตัวอย่าง: ดึงเหตุการณ์ล่าสุด

GET /api/events?limit=20&sort=desc

API สำหรับพันธมิตรภายนอก (Partner API)

นอกจาก REST API ภายในข้างต้น (/api/* — ใช้โดย dashboard และแอปมือถือ) Vigil Platform ยังเปิด Partner API แยกต่างหาก (/v1/*) สำหรับให้พันธมิตรภายนอก (เช่นหน่วยงานที่ต้องการดึงข้อมูลป้ายทะเบียน/เหตุการณ์ไปประมวลผลต่อ) เชื่อมต่อแบบ server-to-server โดยไม่ต้องมี session หรือเบราว์เซอร์เลย

คนละระบบ คนละการยืนยันตัวตนกับ API ภายใน

Partner API เปิดให้บริการบนโดเมนแยก (ไม่ใช่โดเมนของ dashboard) และใช้การเซ็นคำขอด้วยกุญแจ (API Key + Secret เฉพาะพันธมิตรแต่ละราย) แทน cookie/JWT ที่ dashboard ใช้ — ป้องกันไม่ให้ ผู้บุกรุกที่ได้ credential ฝั่งพันธมิตรไปสามารถเข้าถึง dashboard ของผู้ดูแลระบบได้

สิ่งที่พันธมิตรดึงข้อมูลได้

Endpoint ทำอะไร
GET /v1/healthzตรวจสอบว่า credential ยังใช้งานได้
GET /v1/camerasรายชื่อกล้องที่พันธมิตรรายนี้มีสิทธิ์เห็น
GET /v1/lpr/eventsฟีดเหตุการณ์ป้ายทะเบียน ย้อนหลังตามช่วงเวลาที่กำหนด
GET /v1/face/eventsฟีดเหตุการณ์บุคคล/ยานพาหนะ (คุณลักษณะที่ไม่ระบุตัวตน)
POST /v1/lpr/searchค้นหาป้ายทะเบียนที่ต้องการ (รองรับภาษาไทย)
GET /v1/openapi.jsonเอกสาร API แบบมาตรฐาน OpenAPI 3.1 — สร้างขึ้นเฉพาะสำหรับพันธมิตรรายนั้น ตามสิทธิ์จริงที่ได้รับ (endpoint/คอลัมน์ที่ไม่มีสิทธิ์จะไม่ปรากฏในเอกสารเลย ไม่ใช่ปรากฏแต่เรียกไม่ได้)

สิทธิ์เข้าถึงถูกบังคับที่ฐานข้อมูล ไม่ใช่แค่ในโค้ด

ผู้ดูแลระบบกำหนดได้ละเอียดถึงระดับคอลัมน์ว่าพันธมิตรแต่ละรายเห็นข้อมูลอะไรได้บ้าง (เช่น ปิดคอลัมน์ ป้ายทะเบียนไว้จนกว่าจะมีข้อตกลงแบ่งปันข้อมูลที่จำเป็นตามกฎหมาย PDPA) — สิทธิ์นี้บังคับใช้ที่ชั้น ฐานข้อมูลโดยตรง ไม่ใช่แค่เงื่อนไขในโค้ด API เพื่อไม่ให้บั๊กในโค้ดกลายเป็นช่องทางรั่วไหลข้อมูลที่ไม่ได้รับอนุญาต

ระบบป้องกันเพิ่มเติม

  • จำกัดอัตราการเรียก (rate limit) ต่อพันธมิตรแต่ละราย ป้องกันการดึงข้อมูลถี่เกินไป
  • บันทึกทุกคำขอ (audit log) ทั้งที่สำเร็จและถูกปฏิเสธ — เห็นได้ว่าใครพยายามเข้าถึงอะไรบ้าง
  • credential มีวันหมดอายุได้ ตั้งเป็นช่วงเวลา (30/60/90/120/180/365 วัน) และปิดการใช้งานได้ทันทีโดยไม่ต้องลบ
  • เพิ่ม/ถอนสิทธิ์ได้ทุกเมื่อ โดยไม่กระทบการเชื่อมต่อเดิม — ปิดเฉพาะคอลัมน์ที่ต้องการได้ทันที

ต้องการเชื่อมต่อ Partner API ติดต่อผู้ดูแลระบบเพื่อขอ credential — ใช้เวลาตั้งค่าไม่กี่นาที

แหล่งข้อมูลจากระบบภายนอก (Inbound Integrations)

นอกจากเปิดข้อมูลออกให้พันธมิตรแล้ว Vigil Platform ยังดึงข้อมูล "บัญชีเฝ้าระวัง" (บุคคล/ยานพาหนะ) เข้ามาจากระบบภายนอกที่หน่วยงานอื่นดูแลอยู่แล้ว เพื่อให้แจ้งเตือนอัตโนมัติเมื่อกล้องของเราจับภาพตรงกับ รายชื่อเฝ้าระวังนั้น โดยไม่ต้องพิมพ์ข้อมูลซ้ำเอง

ระบบต้นทาง ดึงข้อมูลอะไร ใช้ยืนยันตัวตนแบบไหน
Dahua DSS Pro รายชื่อบุคคล + ยานพาหนะเฝ้าระวังจากระบบตำรวจ/รักษาความปลอดภัย บัญชีที่หน่วยงานเจ้าของระบบมอบให้ ผ่านทาง edge node ในไซต์นั้น
GuruSquare ทะเบียนยานพาหนะเฝ้าระวัง (เฉพาะป้ายทะเบียน) API Key ต่อระบบ
HikCentral Professional (HCP) ค้นหาใบหน้าย้อนหลังข้ามกล้องผ่านดัชนีของ HCP — เฉพาะไซต์ที่มี HikCentral อยู่แล้ว ผ่าน edge node ของไซต์นั้นเท่านั้น (ไม่เปิดให้เข้าถึงตรงจาก central)

เราไม่แก้ไขข้อมูลที่ระบบต้นทางโดยตรง

ถ้าพบข้อมูลที่ผิดพลาดจากระบบต้นทาง (เช่น พิมพ์ชื่อผิด) เราไม่มีสิทธิ์ไปแก้ไขระบบต้นทางเอง — การแก้ไขทำที่ฝั่งเราเป็นชั้นเสริมทับไว้ ครั้งถัดไปที่ดึงข้อมูลใหม่จากต้นทาง ระบบจะยังใช้ค่าที่แก้ไว้ โดยอัตโนมัติ ไม่ต้องแก้ซ้ำทุกครั้ง และไม่มีการลบข้อมูลทิ้งถาวร — "ซ่อน" รายการที่ไม่ต้องการได้ แต่กู้คืนได้เสมอพร้อมประวัติว่าใครซ่อนไว้เมื่อไหร่
