04 องค์ประกอบระบบ

ภาพรวมสถาปัตยกรรม (Architecture Overview)

Vigil Platform ประกอบด้วย 4 ชั้นหลัก: Ingestion (รับเหตุการณ์จากกล้อง), Backend API (ประมวลผล สถิติ), Worker Processes (แจ้งเตือน + รายงาน), Database (เก็บข้อมูล), และ Frontend (dashboard + mobile app)

ระบบทำงานเป็น 8 PM2 processes แยกกัน — ถ้า Chrome/Puppeteer ของ report-worker crash หรือ LINE timeout ใน alert-worker จะไม่กระทบ api-server หรือ MQTT ingester

รองรับ Site Edge Node (VIGIL-ARCH-003) — mini PC (N150/Ubuntu) วางข้างกล้อง รัน ingester ด้วย EDGE_MODE=1 ส่ง events ขึ้น central ผ่าน MQTT bridge แทน direct DB

ชั้น Frontend

Dashboard (Vanilla JS + Chart.js + OpenLayers)

  • Live dashboard: กล้อง เหตุการณ์ การแจ้งเตือน
  • Executive Summary: บรรยายสรุปตอนเช้า KPI
  • Analytics: กราฟเส้นเวลา แนวโน้ม
  • Settings: การตั้งค่ากล้อง กฎ ผู้ใช้
  • Map page: OpenLayers + CartoDB
  • Appearances: ค้นหา + กราฟวิเคราะห์

ชั้น Ingestion

Ingesters เฉพาะเจาะจงตามเวนเดอร์ (Node.js)

  • Bosch: MQTT listener (ONVIF Profile M)
  • Hikvision: ISAPI HTTP endpoint
  • Dahua: HTTP CGI listener
  • ตรวจสอบและปกติของเหตุการณ์
  • ดาวน์โหลดสื่อ (สแนปช็อต บทตัดกล้อง)

Backend API

Express.js REST API

  • ค้นหาเหตุการณ์ เส้นเวลา สถิติ
  • ยืนยันตัวตนผู้ใช้ (JWT + session)
  • RBAC (admin viewer auditor)
  • Health check + Service Management UI
  • Proxy สำหรับ on-demand report run

Worker Processes (PM2)

Isolated background workers

  • alert-worker — รับ pg_notify alert_event → ประมวล rule → ส่ง LINE + push; EM6 edge stale alert ทุก 5 นาที
  • report-worker — scheduler รายงาน (60s tick) + on-demand HTTP 127.0.0.1:3001 — crash isolation ถ้า Puppeteer/Chrome พัง
  • lpr-receiver (PM2 id 8) — standalone ANPR HTTP push receiver (port 3003); รับ LPR + face-push; disk spool/retry สำหรับ LPR forward

ฐานข้อมูล

PostgreSQL (20+ ตาราง)

  • events — บันทึกเหตุการณ์หลัก
  • cameras — การตั้งค่ากล้อง (site_id, cam_role, lpr_direction added)
  • sites, user_sites — Multi-site (Tier 1 ✅)
  • edge_status — Edge Node heartbeat per site (EM2)
  • alert_rules, alert_logs
  • appearances — คุณลักษณะของบุคคล
  • face_event_notes, face_event_acks, face_settings — Face UX (FP4/5/6)
  • lpr_alert_acks, lpr_watchlist_groups — LPR alert ack (RF-Alert)
  • users, audit_logs
  • นโยบายการเก็บรักษา (การลบโดยอัตโนมัติ)
  • Indexes + partition ตามวันที่

ที่เก็บสื่อ

Local filesystem + S3/NAS เพิ่มเติม

  • snapshots/ — รูปภาพเหตุการณ์
  • faces/ — บทตัดใบหน้า Hikvision
  • videos/ — คลิปก่อน alarm (Profile C)
  • Retention: ตั้งค่าได้แต่ละประเภท
  • Cleanup: ลบไฟล์เก่าโดยอัตโนมัติ

บริการสนับสนุน

  • EMQX (สำหรับ Bosch MQTT)
  • Redis (session cache real-time pub/sub)
  • PM2 (8 workers: api-server, mqtt-subscriber, hikvision-isapi, dahua-cgi, media-recorder, lpr-receiver, alert-worker, report-worker)
  • Cloudflare Tunnel (reverse proxy)
  • LINE API (bot webhook)
  • Puppeteer (health report PDF/PNG — ใน report-worker)

Site Edge Node (ตัวเลือก — VIGIL-ARCH-003)

Mini PC (N150/Ubuntu) วางข้างกล้องที่ site

  • รัน ingester ด้วย EDGE_MODE=1 — ไม่ต้องการ DB local
  • NanoMQ — local MQTT broker รับ events จากกล้อง
  • edge-bridge (Node.js) — ส่ง events ขึ้น central EMQX ผ่าน WSS
  • 7 PM2 processes แยกจาก central: nanomq, hikvision, dahua, lpr-receiver, edge-config-agent, edge-bridge, cloudflared
  • Images ไม่ผ่าน MQTT — เฉพาะ metadata + filename ref
  • ใช้เมื่อกล้องอยู่ต่าง network segment หรือต้องการ local resilience

ลำดับการไหลของข้อมูล

รับเหตุการณ์ (Real-time)

กล้อง → [Bosch MQTT | Hik ISAPI | Dahua HTTP] → Ingester Node.js
        → ตรวจสอบ + ดาวน์โหลด snapshot/บทตัดใบหน้า
        → INSERT INTO ตารางเหตุการณ์
        → เผยแพร่ไปยังช่อง Redis (real-time → dashboard WS)
        → pg_notify alert_event → alert-worker (process แยก)
             → ตรวจ alert rules → ส่ง LINE + Push (ถ้าตรงกัน)
        → Return 200 OK

Frontend Real-time (WebSocket)

Frontend → การเชื่อมต่อ WS → Backend
         → [สมัครสมาชิกช่อง alert]
         → Backend เผยแพร่ alert ใหม่ผ่าน Redis
         → WS ส่งไปยังไคลเอนต์ทั้งหมดที่เชื่อมต่อ
         → UI อัปเดต (บัตรเหตุการณ์ใหม่ เสียง toast)

สร้างรายงาน

ผู้ใช้คลิก "สร้างรายงานสุขภาพ"
         → api-server สร้าง SVG template (_svgSafeText ลบ emoji)
         → Sharp (librsvg) render SVG → PNG (ไม่มี emoji = ไม่ abort)
         → ส่งลิงก์ดาวน์โหลด
         → PNG หมดอายุหลังจาก 24 ชั่วโมง (cleanup job)

ผู้ใช้คลิก "Run Now" / Scheduled Report
         → api-server proxy → report-worker (HTTP 127.0.0.1:3001)
         → report-worker ใช้ Puppeteer render HTML → PDF/PNG
         → ถ้า Chrome crash → PM2 restart เฉพาะ report-worker
            api-server ยังออนไลน์ปกติ

ลำดับการยืนยันตัวตนและการอนุญาต

1. เข้าสู่ระบบผู้ใช้ (username + password)
   → Backend ตรวจสอบ credentials (bcrypt)
   → สร้าง JWT token (httpOnly cookie)
   → สร้าง refresh token ด้วย (Redis)

2. ทุกการร้องขอ API
   → ไคลเอนต์ส่ง JWT ผ่าน httpOnly cookie (ไม่ใช่ header)
   → Middleware ตรวจสอบลายเซ็น + ความเท่า expiry
   → แยก user ID + role (admin/viewer/auditor)
   → ตรวจสอบสิทธิ์สำหรับ endpoint

3. การเข้าถึงแบบ role-based (RBAC)
   → admin: เข้าถึงเต็มที่
   → viewer: dashboard read-only
   → auditor: read-only + reports/export

4. Audit log
   → ทุก action ที่สำคัญบันทึกในตาราง audit_logs
   → User ID action timestamp IP address

  • Frontend (nginx)
  • API (Node.js)
  • PostgreSQL
  • Redis
  • EMQX (optional)

Ubuntu/Debian + Node.js โดยตรง

  • Nginx reverse proxy
  • PostgreSQL จัดการแยก
  • Redis จัดการแยก
