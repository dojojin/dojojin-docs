## 2. ของที่มีอยู่แล้ว (สำรวจ 2026-07-31)

**`src/edge/snapshot-retention.js`** — pruner ฝั่ง edge มีอยู่แล้วและ**ทำงานอยู่จริง**
เรียกจาก `src/edge/bridge.js:370` · ครั้งแรกหลัง boot 2 นาที แล้วทุกชั่วโมง

```js
const EDGE_IMG_DAYS = parseInt(process.env.EDGE_IMAGE_RETENTION_DAYS, 10); // NaN → default 7
pruneEdgeSnapshots(SNAPSHOT_DIR, EDGE_IMG_DAYS)
```

**ช่องทางส่ง config ก็มีแล้ว** — `edge-bridge` subscribe `CONFIG_TOPIC` (`bridge.js:194`) และ central มี `publishSiteConfig()` ส่ง config ราย site อยู่แล้ว · **ไม่ต้องสร้างช่องทางใหม่**

**heartbeat ก็มีแล้ว** — `bridge.js:360` ส่งทุก 60 วิ ไปที่ `projects/{SITE_ID}/_edge/heartbeat`

### 🕳️ 3 ช่องโหว่

| # | ช่องโหว่ | หลักฐาน |
|---|---|---|
| **1** | pruner แตะแค่ `events/` — **`lpr/` และ `face/` ไม่เคยถูกลบเลย** | `snapshot-retention.js:33` → `path.join(abs, 'events')` · hkt สะสม LPR 111 GB |
| **2** | `vss` เก็บไฟล์**แบนที่ราก** ไม่มีโฟลเดอร์วันที่ → pruner หาไม่เจอ | pruner หาเฉพาะ `events/YYYY-MM-DD` (`DATE_RE`) |
| **3** | ตั้งผ่าน **env var** ซึ่ง **ไม่มีเครื่องไหนตั้งเลย** (ใช้ default 7) | แก้ต้อง ssh + restart · หน้าเว็บตั้งไม่ได้ · central มองไม่เห็นว่าไซต์ไหนตั้งเท่าไหร่ |

> ⚠️ ที่ `lpr/` ไม่ถูกลบ **เป็นความตั้งใจ** — คอมเมนต์ในโค้ดเขียนไว้ว่า *"edge LPR images may be primary evidence (PDPA/legal weight); that retention is a separate decision"*

## 3. การออกแบบ

**หลักการ: ตั้งที่ central · เก็บใน DB · edge รับผ่าน MQTT ที่มีอยู่แล้ว**

```
Dashboard → Settings › Sites › [ไซต์] → ตั้ง 4 ค่า
        ↓ เก็บใน site_retention (ตารางใหม่)
        ↓ publishSiteConfig() ส่งผ่าน MQTT (ของเดิม)
   edge-bridge รับ → prune ตามค่าของไซต์ตัวเอง (แทนที่จะอ่าน env)
        ↓ heartbeat รายงานกลับ (ของเดิม)
   central เห็นบนหน้า Health: ดิสก์เหลือ · prune ล่าสุดเมื่อไหร่ · ค่าที่ไซต์นั้นใช้อยู่
```

### ค่าที่ตั้งได้ต่อไซต์

| ชนิด | โฟลเดอร์ | ปัจจุบัน | หลังทำ |
|---|---|---|---|
| Events snapshot | `events/` | 7 วัน (default, ตั้งไม่ได้) | ตั้งได้รายไซต์ |
| **LPR image** | `lpr/` | **ไม่ลบเลย** | **baseline 6 วัน** ← เจ้าของเคาะ |
| **Face image** | `face/` | **ไม่ลบเลย** | **baseline 6 วัน** ← เจ้าของเคาะ |
| กันดิสก์เต็ม | ทุกโฟลเดอร์ | ไม่มี | `min_free_gb` ต่อไซต์ |

> **6 วันสอดคล้องกับของเดิม** — central ตั้ง `lpr_image_retention_days = 6` อยู่แล้ว การใช้ 6 วันที่ edge ด้วยทำให้ทั้งสองฝั่งหมดอายุพร้อมกัน ไม่เกิดสภาพ "central ลบแล้วแต่ edge ยังเก็บ"

**metadata ที่ส่งเข้า central ไม่กระทบเลย** — คนละ path กัน · ลบรูปที่ edge แล้ว event/ป้ายทะเบียนใน central ยังครบ · หน้า dashboard มี fallback อยู่แล้ว (plaque / vehicle vector) เมื่อรูปหมดอายุ

### Optimize ที่แถมมาในตัว

1. **ลบตาม "พื้นที่เหลือ" ไม่ใช่แค่ "อายุ"** — ถ้าเหลือน้อยกว่า `min_free_gb` ให้ลบวันเก่าสุดเพิ่มทันทีโดยไม่รอครบกำหนด → **hdy จะไม่มีวันเต็ม**
2. **แจ้งเตือนก่อนเต็ม** — heartbeat มีอยู่แล้ว เพิ่มเตือนเมื่อเหลือ < 15% หรือ prune ไม่ทำงานเกิน 3 ชม.
3. **hkt ได้ประโยชน์ทันที** — RAID 3.6 TB ใช้ไป 4% แต่ถูกจำกัดที่ 7 วันเท่า vss ที่มี 117 GB
4. **แก้ layout ของ vss** ให้ pruner หาเจอ

## 4. แบ่งเป็น 4 ขั้น

| ขั้น | งาน | ได้อะไร | เสี่ยง |
|---|---|---|---|
| **R1** | ตาราง `site_retention` + UI ใน Settings › Sites + ส่งผ่าน MQTT · edge อ่านจาก config แทน env | ตั้ง **Events snapshot** แยกรายไซต์ได้ | ต่ำ — ยังไม่แตะ `lpr/`/`face/` |
| **R2** | กฎ `min_free_gb` + แจ้งเตือนดิสก์ใกล้เต็ม / prune ค้าง | **hdy ปลอดภัยจากดิสก์เต็ม** | ต่ำ — ป้องกันอย่างเดียว |
| **R3** | ขยาย pruner ให้ครอบ `lpr/` + `face/` · **baseline 6 วัน** | ครบทั้ง 3 ชนิด | ⚠️ ลบข้อมูลที่เคยเก็บถาวร — ดูข้อควรระวังด้านล่าง |
| ~~**R4**~~ | ~~แก้ layout ของ vss~~ ✅ **ปิดแล้ว 2026-07-31 — ไม่ต้องแก้ pruner** | — | — |

**R1+R2 เริ่มได้ทันทีโดยไม่ต้องรออะไร** และแก้ปัญหาที่เร่งด่วนที่สุด (hdy) ไปแล้ว

### ⚠️ ข้อควรระวังของ R3

- **hkt มี LPR สะสม 111 GB ที่ไม่เคยถูกลบ** — วันแรกที่เปิด R3 ด้วย 6 วัน จะลบของเก่าเกือบทั้งหมดในครั้งเดียว
  → **ต้องมีโหมด dry-run และรายงานว่าจะลบเท่าไหร่ ก่อนลบจริง**
- `face/` เป็นข้อมูลชีวมิติ PDPA คุมเข้มกว่า LPR — 6 วันเท่ากันคือ baseline แต่**ควรทบทวนกับฝ่ายกฎหมายก่อนใช้จริง**
- ลบแล้วไม่มีทางกู้ — รูปที่ edge เป็นต้นฉบับ ไม่ได้ copy ไป central (ยกเว้น Bosch crop)

## 6. R4 — ปิดเคสแล้ว 2026-07-31 · **สมมติฐานเดิมผิด**

แผนเขียนว่า *"vss เก็บไฟล์แบนที่ราก ไม่มีโฟลเดอร์วันที่ → pruner หาไม่เจอ"* — จริงตอนสำรวจ
แต่ **ไม่ใช่ปัญหาที่ยังเกิดอยู่** ตรวจของจริง 2026-07-31:

```
snapshots/
  events/   ← 4,725 ไฟล์ · เขียนอยู่จริง (1,239 ไฟล์ใน 24 ชม.)
  face/     ← 18,324 ไฟล์ · เขียนอยู่จริง (956 ไฟล์ใน 24 ชม.)
  preview/  ← เขียนอยู่จริง
  *.jpg     ← 410 ไฟล์ · 139.7 MB · ทุกไฟล์ลงวันที่ 2026-06-25 วันเดียว · ไม่มีอะไรเขียนมาเดือนกว่าแล้ว
```

vss **ใช้ layout เดียวกับไซต์อื่นอยู่แล้ว** และ pruner ทำงานปกติ (heartbeat รายงาน
`retain 7 · cutoff 2026-07-24`) · ไฟล์แบนที่รากเป็น**ของตกค้างจากโค้ดเวอร์ชันเก่า** ไม่ใช่ layout ปัจจุบัน

**ทางแก้ที่ถูกจึงไม่ใช่การสอน pruner ให้อ่านไฟล์แบน** — นั่นคือการสร้างกลไกถาวรเพื่อไฟล์
ตกค้าง 410 ไฟล์ที่ไม่มีวันเพิ่มขึ้นอีก · ทางที่ถูกคือลบทิ้งครั้งเดียว

ตรวจก่อนลบ: `events.snapshot_filename` ที่ขึ้นต้นด้วย `BMA-EAST_DAHUA_CAM01_` เหลือ **0 แถว**
ในฐานข้อมูล → ไม่มี event ไหนอ้างถึงไฟล์เหล่านี้เลย · อายุ 36 วัน เกินอายุเก็บรูปของ edge (6-7 วัน) ไปนาน

ลบแล้ว: **410 ไฟล์ · 139.7 MB** · `events/` `face/` `preview/` ไม่ถูกแตะ (ใช้ `-maxdepth 1` กันไว้)
