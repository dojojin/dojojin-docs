## 3. สถาปัตยกรรมตอนนี้ vs ที่จะเป็น

### ตอนนี้ — สองเส้นทางแยกกันสิ้นเชิง

```
กล้อง face ─push (httpHost slot 1)──────────────► CIB 202.124.201.105:10001/v2/<UUID>
        └──pull (ISAPI alertStream) ── edge (hikvision-isapi.js) ── Vigil
```

ถ้า CIB ล่ม กล้องพยายามส่งเองแล้วทิ้ง — เราไม่รู้ ไม่มี spool ช่วย

### เทียบกับ LPR ที่ทำไปแล้ว

```
กล้อง LPR ─push──► edge:3003/lpr/<token> ──► lpr-receiver ─┬─► Vigil (ingest)
                                                           └─► CIB .106:10001/receive_hik_phuget
                                                               (มี spool/retry 6 ชม.)
```

### ที่จะทำ — เหมือน LPR

```
กล้อง face ─push──► edge:3003/face-push/<token> ──► face-push ─┬─► Vigil (ingest)
                                                               └─► CIB .105:10001/v2/<UUID>
                                                                   (spool/retry)
```

**ความต่างสำคัญจาก LPR:** LPR ทุกตัวยิงเข้า path เดียวกัน (`/receive_hik_phuget`)
แต่ face **มี UUID เฉพาะตัวต่อกล้อง** → ตัว forward ต้องเก็บ UUID ของแต่ละกล้อง
แล้วยิงไป path ที่ถูกตัว ถ้าสลับ = CIB บันทึกว่าเป็นกล้องผิดจุด

## 5. "Subscription ของ CIB" — ตรวจแล้วพบว่ามีแค่ทางเดียวที่ยืนยันได้

คำว่า subscription อาจหมายถึงได้ 3 กลไก ตรวจทีละอย่าง:

| กลไก | ตรวจยังไง | ผล |
|---|---|---|
| **A. Push ผ่าน httpHost** (กล้องยิงหา CIB) | อ่าน `/ISAPI/Event/notification/httpHosts` ทั้ง 34 ตัว | ✅ **ยืนยันแล้ว** — 33 ตัวชี้ `.105:10001/v2/<UUID>` |
| **B. Subscribe ผ่าน ONVIF MQTT broker** | เรียก `GetEventBrokers` ผ่าน `/event-broker-status` | ❌ กล้องตอบ **HTTP 404 / 500** — รุ่นนี้ไม่รองรับหรือปิดอยู่ |
| **C. Pull ผ่าน ISAPI alertStream** (CIB ต่อค้างไว้เอง) | ⚠️ **มองจากฝั่งเราไม่เห็น** | ต้องถาม CIB หรือดู "ผู้ใช้ที่ออนไลน์" ในหน้าเว็บกล้อง |

> **สิ่งที่ต้องเข้าใจให้ตรงกันก่อนวางแผน:** ที่เราเห็นคือ **กล้องยิงไปหา CIB (push)**
> ไม่ใช่ CIB มาดึงจากกล้อง. การ "ย้ายมาที่เรา" จึงเป็นการ**แก้ค่าบนกล้อง** ซึ่งเราทำได้เอง
> — **ไม่ต้องให้ CIB แก้อะไรในระบบเขา** ตราบใดที่เรายิงเข้า path เดิมด้วย UUID เดิม
>
> **แต่ถ้ามีกลไก C อยู่ด้วย** (CIB ต่อ ISAPI ค้างไว้) การย้าย push อย่างเดียวจะไม่ครบ
> และ session ที่ CIB ถือไว้จะยังกิน slot ของกล้องต่อไป — **ต้องเคลียร์ข้อนี้ก่อนเริ่ม F2**

### หลักฐานฝั่งเรา (จาก edge ภูเก็ต)

```
39 ESTAB    → alertStream ที่ "เรา" ต่อค้างไว้กับกล้อง 35 ตัว
55 SYN-SENT → พยายามต่อกล้องที่ยังไม่ได้ติดตั้ง 34 ตัว วนไม่เลิก
```

**ทั้ง 94 connection เป็นของเราเอง** (ต้นทาง `10.0.10.50`) — มองไม่เห็น connection ของ CIB
เพราะเรานั่งดูจาก edge ไม่ใช่จากกล้อง

### 🔄 F4 — **เลื่อนตัดสิน 2026-08-06** · เดินด้วย "pull ingest · push relay" ไปก่อน

**เดิมวางไว้ว่า:** ปิด alertStream ของกล้องนำร่อง → ให้ ingest ผ่าน push ทางเดียว

**ทำไมยกเลิก:** คำถามของเจ้าของ *"เราใช้ pull แต่ส่งให้ CIB โดย push — เราไม่จำเป็นต้อง
push ที่กล้องเหมือนเขาใช่ไหม"* ชี้ว่า **สองเรื่องนี้แยกกันได้**

- `alertStream` (pull) **ไม่กิน alarm-server slot** — คนละกลไกกัน
- slot ที่จองบนกล้อง มีไว้เพื่อ **relay ไบต์ดิบต่อให้ CIB** เท่านั้น ไม่ใช่เพื่อ ingest
- `face-push.js` ยิง `forwarder.forward(req.body, ct, url)` **ก่อน parse เสมอ** แล้ว
  `return` ทิ้งถ้า parse ไม่ออก → **"relay อย่างเดียว ไม่ ingest" คือพฤติกรรมของโค้ดปัจจุบันอยู่แล้ว**

**สถาปัตยกรรมที่ใช้แทน:**
```
กล้อง ──alertStream (pull)──► เรา ingest          (เดิม พิสูจน์แล้ว 874/874)
กล้อง ──slot 1 push─────────► เรา relay ดิบ ──► CIB   (ไม่ ingest)
slot 2 ปิด
```

**ได้อะไร:** ปัญหา event ซ้ำ 2 เท่าหายไปเอง · ไม่ต้องเขียน dedup · ไม่ต้องแตะ ingest path เลย
· pull กับ push วิ่งคู่กันเป็น **cross-check ถาวร** (ส่วนต่าง = CIB กำลังขาดของ)

#### ❌ สมมติฐาน "CIB กรองด้วย header" — **พิสูจน์แล้วว่าผิด** (2026-08-06, commit `8715ec4`)

`_describeHeaders()` เก็บของจริงจาก `C23WIC-SB-17` ได้ **กล้องส่งมาแค่ 4 header**:
```
content-type: multipart/form-data; boundary=boundary
host: 10.0.10.50:3003
connection: close
content-length: 687668
```
**ไม่มี `User-Agent` เลย** — ที่เดาว่า gateway กรอง `User-Agent` จึงตกไป

ต่างจากของกล้องแค่ **`Connection: close` vs `keep-alive`** เท่านั้น

## 9. เรื่องที่เจอระหว่างสำรวจ — ไม่เกี่ยวกับแผนนี้แต่ควรแก้

**edge วนต่อกล้องที่ไม่มีอยู่จริง — 55 connection ค้าง SYN-SENT**

```

55 SYN-SENT  → พยายามต่อกล้อง 34 ตัวที่ enabled=false  (เปล่าประโยชน์)
```

กล้องที่ `enabled=false` ในระบบกลาง แต่ ingester ที่ edge ยังพยายามต่อวนไม่เลิก
— เปลือง socket + timeout thread และทำให้ log รก **ไม่ใช่ความเสี่ยงของแผนนี้**
แต่ควรทำ: ให้ ingester เคารพ `enabled` หรือถอย backoff เมื่อ SYN ไม่ผ่านติดกันหลายครั้ง

### 11.6 🔴 โค้ดไม่ตรงกับแผน F4 — push ยัง parse อยู่
