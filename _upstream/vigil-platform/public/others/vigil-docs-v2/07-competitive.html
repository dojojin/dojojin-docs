07 Architecture Decisions (การออกแบบสถาปัตยกรรม)

ทำไมต้อง Self-hosted ไม่ใช่ SaaS Cloud?

ข้อดีของ Self-hosted

  • Data sovereignty: ข้อมูลในประเทศไทย PDPA compliant
  • Lower TCO: ซื้อครั้งเดียว + Maintenance Agreement รายปี ≠ ค่าบิล cloud รายเดือนตลอด
  • No vendor lock-in: ลูกค้าเป็นเจ้าของข้อมูล + infrastructure
  • Customization: ลูกค้า + System Integrator ขยายแก้ไขได้เอง
  • Privacy: ข้อมูลอยู่บน premise ลูกค้าเท่านั้น

ข้อเสียของ Self-hosted

  • Deployment complexity: ลูกค้าต้องมี IT team
  • No managed service: ลูกค้าเป็นเจ้าของ monitoring, backup, updates
  • Scaling DIY: ถ้าเพิ่มกล้องต้องเพิ่ม hardware เอง
  • Support cost: System Integrator ต้อง train + support ลูกค้า
  • Churn: ลูกค้าจำหน่ายเครื่องและเลิกจ่าย Maintenance Agreement

ตัดสินใจสำคัญเกี่ยวกับ Tech Stack

Vanilla JavaScript (ไม่ใช่ React/Vue/Svelte)

เหตุผล: Dashboard ไม่ซับซ้อน เพียง CRUD + real-time updates ด้วย WebSocket — ค่าใช้จ่าย React ไม่ชดใช้

  • Bundle size: ~50KB (เทียบกับ ~100KB+ React + dependencies)
  • ไม่ต้องมี build step (webpack, babel)
  • ควบคุม DOM โดยตรง (performance-critical map page)
  • Easier onboarding สำหรับ System Integrator ที่ติดตามโค้ด

Trade-off: ไม่มี component reuse, manual state management

Raw SQL (ไม่ใช่ ORM)

เหตุผล: Queries ซับซ้อน (window functions, partitions, time-series) — ORM ทำให้ยากขึ้น

  • ควบคุม query optimization อย่างเต็มที่
  • Explicit explain plans + index tuning
  • Migration flexibility (raw SQL idempotent scripts)
  • Dependencies น้อยกว่า (Prisma, Drizzle = large dependency graph)

Trade-off: manual parameterization, more testing

Express.js (ไม่ใช่ NestJS/Fastify)

เหตุผล: Lightweight, proven, no hidden magic, easy debugging

  • Middleware ecosystem ครบครัน (passport, cors, helmet)
  • Minimal overhead เทียบกับ Fastify (ไม่ latency-critical)
  • NestJS = over-engineered สำหรับ CRUD API นี้

Trade-off: ไม่มี built-in TypeScript, manual setup

OpenLayers (ไม่ใช่ Mapbox/Leaflet)

เหตุผล: Powerful, open-source, multi-projection support, ไม่ต้อง commercial token

  • CartoDB + OSM tiles (ฟรี, ไม่ต้อง auth)
  • Native clustering + heatmap
  • Leaflet ง่ายเกินไป Mapbox แพงและ proprietary

Trade-off: steeper learning curve, larger bundle

EMQX (ไม่ใช่ Mosquitto)

เหตุผล: Bosch MQTT → ต้องการ scalability clustering + auth

  • Clustering support (multi-node HA)
  • Better memory management + throughput
  • Mosquitto ใช้ได้สำหรับ single-broker small scale

Trade-off: added complexity, learning curve

PostgreSQL (ไม่ใช่ MySQL)

เหตุผล: Advanced features (JSON, window functions, LATERAL JOIN)

  • JSON native type สำหรับ IVA metadata
  • Window functions สำหรับ analytics
  • Partitioning by date เหมาะกับข้อมูลขนาดใหญ่
  • ACID ที่เข้มแข็งขึ้น

Trade-off: heavy นิดหน่อยกว่า MySQL, config มากขึ้น

Puppeteer + Sharp (ไม่ใช่ Puppeteer อย่างเดียว)

เหตุผล: Health Report PNG rendering ต้อง SVG + ไม่มีปัญหา emoji

  • Sharp = fast image processing (C++ binding)
  • Puppeteer + librsvg abort บน emoji → Sharp แก้ปัญหา
  • ดีกว่า Wkhtmltopdf (deprecated) หรือ headless Chrome (memory heavy)

Trade-off: 2 dependencies, extra config

Deployment Architecture: ทำไมต้อง Docker + PM2?

ตัวเลือก ข้อดี ข้อเสีย ตัวเลือกของ Vigil
Docker Compose + Reproducible, all-in-one, easy first-time setup - Container orchestration DIY, ไม่มี HA out-of-box ✅ Primary (dev + small prod)
Kubernetes + Auto-scaling, HA, industry standard - Overkill สำหรับ single-server, learning curve ⏳ Roadmap Ph.6 (สำหรับลูกค้ากำลังใหญ่)
PM2 on VM + Lightweight, auto-restart, clustering บน single server - ไม่มี container isolation, manual setup ✅ Secondary (bare-metal, existing VM)
systemd เท่านั้น + Native, ไม่ต้องเครื่องมือเพิ่มเติม - ไม่มี process clustering, limited features ❌ ไม่เลือก (PM2 better UX)

ทำไมต้องสองภาษา (TH + EN)?

  • ตลาด: ประเทศไทยเป็นตัวจริง ASEAN เป็นตัวรอง → ภาษาอังกฤษเพื่อขยายในระดับภูมิภาค
  • ผู้ปฏิบัติการ: พนักงาน hotel/industrial = ไทย, บริหารองค์กร = ภาษาอังกฤษผสมกัน
  • รายงาน: Customer-facing (ไทย) + corporate report (ตัวเลือกภาษาอังกฤษ)
  • การบำรุงรักษา: i18n dictionary ใน `dashboard/i18n.js` (2 blocks: `th` + `en`) — ไม่ใช้ gettext (ง่ายกว่าสำหรับทีม)

ทำไมต้อง Mobile App (React Native)?

  • ผู้ปฏิบัติการต้องการ mobile alerts: พนักงาน security เดินตรวจสอบไม่ได้นั่งอยู่ที่โต๊ะ
  • iOS + Android จาก codebase เดียว: เร็วขึ้นในการนำสินค้าออกสู่ตลาด
  • React Native vs Flutter: Ecosystem ที่ใหญ่กว่า ค้นหาวิศวกรได้ง่ายขึ้น JavaScript background ช่วยในการ onboard ทีม
  • Push notifications + Biometric: Native capabilities สำคัญสำหรับ security use case

ปรัชญาการออกแบบ: หลักการสิทธิด้อยที่สุด

Security by default ไม่ใช่ "เปิดแล้วมาล็อก":

  • Ports ปิดตามค่าเริ่มต้น whitelist IPs ที่ชัดเจน
  • Database user สิทธิน้อยสุด (ไม่มี DROP TABLE)
  • Docker ทำงาน non-root
  • RBAC: viewer = read-only, operator = edit own scope, admin = full
  • API endpoints ต้องการการพิสูจน์ตัวตน (ไม่มี public endpoints ยกเว้น health check)

Trade-offs อย่างต่อเนื่อง: ความเร็วกับ Maintainability

Vigil เริ่มต้น lean: Vanilla JS, raw SQL, direct Node.js สิ่งนี้ช่วยให้ MVP ได้เร็ว (v1.0–1.2) ตอนนี้ที่ v1.5, codebase กำลังโตขึ้น → ต้องการ refactor tooling (TypeScript มาใน Ph.6) โดยไม่ทำให้ deployments หัก Strategy: backwards-compatible migrations, feature flags สำหรับ breaking changes
