12 กลยุทธ์การขยายสเกล

ชั้นการตั้งค่าฮาร์ดแวร์ (G1–G5)

Vigil Platform ออกแบบให้สามารถขยายสเกลได้เชิงเส้นตามจำนวนกล้องและความเข้มข้นของเหตุการณ์

ชั้น จำนวนกล้อง เหตุการณ์/วัน (ทั่วไป) พื้นที่เก็บข้อมูล (Snap+Clip 30 วัน) คอนฟิกเซิร์ฟเวอร์ การปรับใช้
G1 Starter ≤100 20,000 ~600 GB i5-13500 (14C) / 24 GB RAM Docker Compose all-in-one (1 เซิร์ฟเวอร์)
G2 Standard 100–500 100,000 ~3.5 TB Xeon E-2486 (8C) / 48 GB RAM Docker Compose + NAS (1–2 เซิร์ฟเวอร์)
G3 Pro 500–1,000 200,000 ~7 TB Xeon Silver 4416+ / 96+128 GB App + DB แยกเครื่อง (2–3 เซิร์ฟเวอร์)
G4 Enterprise 1,000–2,000 400,000 ~15 TB Xeon Gold 6338 / 128+ GB (~11 nodes) HA cluster (API ×2, DB Patroni, MinIO)
G5 Datacenter 2,000–3,000 600,000 ~25 TB Xeon Platinum / 384 GB (~32+ nodes) Multi-zone Kubernetes (Ph.6+)

พื้นที่เก็บข้อมูลรวม snapshot 30 วัน + pre-alarm clip 30 วัน (อัตราส่วน clip 30%) เหตุการณ์/วัน = สถานการณ์มาตรฐาน 200 เหตุการณ์/กล้อง/วัน

รูปแบบการปรับใช้

G1–G2: Single-Server Docker (Profile A–B)

[อินเทอร์เน็ต] → [Cloudflare Tunnel] → [Single VM]
                                    ├─ Frontend (nginx)
                                    ├─ API (Node.js PM2 ×2 workers)
                                    ├─ PostgreSQL
                                    ├─ Redis
                                    └─ Media storage (/mnt/snapshots NAS)
  • ข้อดี: ง่าย คุ้มค่า backup ง่าย
  • ข้อเสีย: จุดล้มเหลว single point of failure ไม่สามารถ horizontal scale ได้

G3–G4: 2-Tier + Replication (Profile B–C)

[อินเทอร์เน็ต] → [Load Balancer (nginx)] → [API VM 1, 2, ...]
                                          ↓
                                      [PostgreSQL Primary]
                                          ↓
                                      [PostgreSQL Replica]
                                          ↓
                                      [NAS (snapshots, videos)]
  • ข้อดี: HA, horizontal API scaling, read replica DB queries
  • ข้อเสีย: ซับซ้อนมากขึ้น พิจารณา replication lag

G5: Kubernetes (Future Ph.6+)

[Ingress] → [Service: API pods × 3–5 (auto-scaling)] → [StatefulSet: PostgreSQL]
                                                        → [PVC: storage (snapshots)]
  • ข้อดี: True auto-scaling, self-healing, multi-zone ready
  • ข้อเสีย: ต้องมีความเชี่ยวชาญ K8s ภาระการจัดการปฏิบัติการสูงขึ้น

กลยุทธ์การขยายฐานข้อมูล

การเพิ่มประสิทธิภาพคำค้นหา (G1–G4)

  • การสร้างดัชนี: (camera_id, event_time, event_type) สำหรับ event queries
  • การแบ่งพาร์ติชัน: ตารางเหตุการณ์ตามเดือน (ลบ partition เดิมโดยอัตโนมัติ)
  • Materialized views: pre-aggregate hourly stats เพื่อหลีกเลี่ยง full table scans
  • Read replica: นำ analytics queries ไปยัง replica (ไม่มี lock contention บน primary)

นโยบายการเก็บรักษาข้อมูล

ประเภทข้อมูล TTL ค่าเริ่มต้น TTL สูงสุด สามารถปรับแต่ง
เหตุการณ์ (ทุกประเภท) 90 วัน 730 วัน (2 ปี) ใช่ (admin setting)

Appearances metadata 30 วัน 730 วัน ใช่

Audit logs 365 วัน 2190 วัน (6 ปี) จำกัด (legal hold)

เส้นทางการย้ายข้อมูล (อัปเกรดลูกค้า)

ลูกค้าเริ่มต้น G1 (50 กล้อง) → เติบโตเป็น G3 (500 กล้อง)

ขั้นตอนที่ 1: ประเมินการเติบโต (ไทม์ไลน์ เหตุการณ์ที่คาดว่าจะเกิด/ชั่วโมง)
ขั้นตอนที่ 2: วางแผน infrastructure ใหม่ (G3 ต้อง separate DB server + load balancer)
ขั้นตอนที่ 3: Backup ระบบ G1 ปัจจุบัน (snapshot full DB)
ขั้นตอนที่ 4: Spin up G3 infrastructure
ขั้นตอนที่ 5: Restore DB → ตรวจสอบความเสมือนสมต้องของข้อมูล
ขั้นตอนที่ 6: Switchover DNS (old IP → new load balancer IP)
ขั้นตอนที่ 7: Monitor 48 ชั่วโมง ทำความสะอาดฮาร์ดแวร์เดิม
เวลาหยุดทำงานที่คาดว่าจะเกิด: 0–5 นาที (ถ้าใช้ DNS TTL 60 วินาที)

ขยายสเกลเกิน 3,000 กล้อง

สำหรับลูกค้าที่มี 3,000+ กล้องหรือ >30K เหตุการณ์/ชั่วโมง:

  • Multi-region: Split deployment ตามภูมิศาสตร์ (Bangkok office + branch office = separate Vigil instances, federated dashboard)
  • Sharding: Database sharding by camera_id (advanced requires application changes)
  • Event streaming: Kafka for async event processing (Ph.6+)
  • BI warehouse: Sync PostgreSQL → BigQuery / Snowflake สำหรับ long-term analytics
