Product Review

1. Product positioning ชัดและมีเหตุผล

Vigil Platform วางตัวเป็น CCTV analytics platform สำหรับองค์กรที่ต้องการควบคุมข้อมูลเอง จุดยืนนี้แข็งแรง เพราะ media เป็นข้อมูลละเอียดอ่อน, latency สำคัญ, กล้องแต่ละ vendor มี event shape ไม่เหมือนกัน และ operator ไทยมักใช้ LINE เป็นช่องทางแจ้งเตือนจริง

จุดดีด้าน product

  • รองรับ Thai-first workflow พร้อม English layer
  • LINE alert/report delivery ตรงกับพฤติกรรมผู้ใช้งานไทย
  • Self-hosted ช่วยเรื่อง PDPA และ vendor lock-in
  • Multi-vendor ลดการผูกกับ Bosch อย่างเดียว
  • มี branding/license/EULA ทำให้ productization จริงจัง

ความต่างจาก dashboard ทั่วไป

  • ไม่ได้แค่แสดง event แต่มี alert engine, report scheduler, health report
  • มี operational history: audit log, alert log, camera status log, report history
  • มี route และ data boundary สำหรับ private snapshots/media
  • มี gotchas จาก incident จริง สะท้อน production learning

วิเคราะห์ Architecture ภาพรวม

Architecture

Camera vendors
  -> MQTT / ISAPI / CGI / RTSP
  -> Ingester processes + media-recorder
  -> PostgreSQL events + snapshots/clips metadata
  -> api-server.js + routes + WebSocket
  -> Vanilla JS dashboard + LINE/report workers

จุดที่ architecture แข็งแรง

Process separation

การแยก alert-worker, report-worker, media-recorder, mqtt-subscriber, hikvision, dahua ออกจาก API server ลด blast radius ได้ดี

Database-centered event pipeline

PostgreSQL เป็น event ledger ที่ดีสำหรับระบบนี้ เพราะต้อง query history, aggregate stats, report, audit

pg_notify เหมาะกับ scale ปัจจุบัน

LISTEN/NOTIFY ให้ realtime glue ที่เบาและตรงโจทย์ ไม่ต้องเพิ่ม Kafka/Redis ก่อนจำเป็น

No framework frontend มีเหตุผล

Vanilla JS ลด build complexity, ลด dependency risk, และเหมาะกับ dashboard ที่ deploy ผ่าน static assets

จุดที่ architecture ยังควรระวัง

  • api-server.js ยังเป็น composition root ขนาดใหญ่ 1,893 lines แม้ route split แล้ว
  • src/routes/cameras.js 1,186 lines รวมหลาย concern: config, EMQX provision, probe, snapshot, audit, status
  • src/routes/health.js รวม health detail, service control, report render/send-now ในไฟล์เดียว 631 lines
  • Event table scale/partition ยังเป็น deferred plan ไม่ใช่ default path
Architectural verdict: โดยรวม architecture "เลือกน้อยแต่ถูก" มากกว่า "กระจาย service เกินจำเป็น" การเลือก raw SQL, PM2, Docker, pg_notify, vanilla JS เป็นชุดที่ practical และ owner เข้าใจได้

วิเคราะห์ Security Posture

Security Review

ภาพรวม: security posture ดีขึ้นมากหลัง hardening รอบก่อน โดยเฉพาะ CSP, auth gate, private media, RBAC, secret hygiene และ EMQX auth แต่ยังต้องเพิ่ม integration smoke tests

จุดแข็ง

  • Global /api auth gate: ลดโอกาสลืมใส่ auth middleware ใน route ใหม่
  • RBAC: admin/viewer/auditor/internal token แยกหน้าที่ชัดเจน
  • Private media: snapshots/media/dashboard private assets ไม่ถูก public โดย default
  • CSP: dashboard และ /others มี Content-Security-Policy ที่ลด CDN/inline script risk
  • Credential handling: camera credential encryption, log redaction, env ignored
  • EMQX auth: MQTT 1883 เปิด LAN ได้โดยมี AUTHN เป็น boundary
  • Audit log: camera/user/admin actions มี audit trail ช่วย governance

Deep Coding Review

1. Coding philosophy: pragmatic, incident-driven, production-aware

โค้ดของระบบนี้มีลักษณะ pragmatic ชัดเจน: ไม่ over-engineer ด้วย framework/ORM/microservices เกินจำเป็น แต่เพิ่ม guard ตาม incident จริง เช่น Safari ITP, Cloudflare cache, EMQX broker, macOS LNP, Health Report SVG emoji crash, camera invisible character

2. Module boundaries

LayerPattern ที่เห็นคุณภาพข้อควรปรับ
Routesmodule.exports = function routes(app, pool, deps)ดี: dependency injection แบบง่ายไฟล์ใหญ่ควรแตก domain helpers
Workersprocess แยก + DB/HTTP/pg_notify integrationดีมาก: blast radius ต่ำกว่า monolith loopเพิ่ม worker health smoke tests
HelpersrouteError, digestAuth, getSystemSetting, normalizeTimeOfDayดี: helper-first เริ่มชัดควร extract เพิ่มจาก large routes
Frontend pagesglobal functions/page modulesเหมาะกับ vanilla JS แต่ต้องมี disciplineเพิ่ม shared render utilities

3. Error handling

  • Backend เริ่มมี routeError helper และหลาย route แยก expected validation error กับ server error
  • Network/camera/probe errors ควร sanitize เพื่อไม่ leak internal details เกินจำเป็น
  • Health endpoint ควร degrade section แทน fail ทั้ง response

4. SQL coding

Checklist ที่ควร enforce ใน review: user input ต้องเข้าผ่าน $n; dynamic column/table/order field ต้องผ่าน allowlist; SQL fragments ที่ interpolate ได้ต้องเป็น constants หรือ derived จาก enum เท่านั้น

5. Async/concurrency design

  • ใช้ pg_notify เป็น event bus เบา ๆ เหมาะกับ scale ปัจจุบัน
  • ใช้ execFile/spawn กับ arg array ในหลายจุด ลด shell injection risk
  • มี PM2 restart/backoff ลดผลกระทบจาก transient failures
  • ควรเพิ่ม timeout และ cancellation discipline ใน health/worker probes
