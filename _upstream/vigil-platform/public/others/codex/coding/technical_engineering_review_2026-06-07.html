1. บทสรุป

Vigil Platform เป็นระบบ production-oriented ที่พัฒนาเกินระดับ prototype แล้ว จุดแข็งคือ architecture ที่ตอบโจทย์จริง, multi-process isolation, raw SQL ที่ควบคุมได้, audit/security hardening หลายชั้น, project memory ดี และ feature breadth ครบสำหรับ security operations จุดอ่อนหลักคือ core files ยังใหญ่, integration tests ยังบาง, frontend ยังเป็น monolith, browser supply-chain ยังต้อง harden และ scale proof ยังต้องทำเชิงระบบ
Engineering maturity ดี

มี PM2, migrations, worker split, auth gates, audit logs, docs และ test harness แล้ว

Maintainability risk ต้องจัดการ

`api-server.js` และ `dashboard.js` ใหญ่ ทำให้ regression และ onboarding cost สูง

Scale readiness ยังต้องพิสูจน์

มี partition plan และ pooling แล้ว แต่ยังขาด benchmark/EXPLAIN/load test ที่ใช้เป็นหลักฐานได้

3. System Architecture Review

3.1 สิ่งที่ออกแบบดี

  • Modular monolith + workers เป็นทางเลือกที่เหมาะ: ระบบไม่ได้กระโดดไป full microservices แต่แยก process ที่เสี่ยง crash หรือ block เช่น alert/report/ingester ออกแล้ว
  • PostgreSQL เป็น center of gravity ที่ถูกต้อง: events, audit, sessions, reports, alert logs และ settings มี source of truth ชัด
  • LISTEN/NOTIFY เหมาะกับ workload: ใช้เป็น event bridge ภายใน host ได้ดี โดยไม่ต้องเพิ่ม queue infrastructure หนัก
  • Vendor-specific ingesters แยกไฟล์: Bosch/Hikvision/Dahua มี behavior ต่างกันมาก การแยก ingester เป็น boundary ที่ถูกต้อง
  • PM2 + Docker split pragmatic: DB/MQTT ใช้ Docker, Node workers ใช้ PM2 เหมาะกับ single-host edge deployment

3.2 จุดเปราะบาง

  • api-server ยังเป็น god-file บางส่วน: แม้เริ่มแยก `src/routes/categories.js` แล้ว แต่ route หลักส่วนใหญ่ยังอยู่ไฟล์เดียว
  • worker orchestration ยังพึ่ง process convention: ถ้า env/internal token mismatch อาจกลายเป็น failure แบบ operational มากกว่า compile-time
  • system boundary ระหว่าง config JSON กับ DB ต้องระวัง: camera config อยู่ JSON แต่ runtime state อยู่ DB เป็น design ที่มีเหตุผล แต่ต้องมี guard กัน drift ต่อเนื่อง
  • ไม่มี formal job queue: ตอนนี้ pg_notify/HTTP callback พอเหมาะ แต่ถ้า scheduled reports/alerts หนักขึ้นอาจต้องมี durable queue table
Architecture grade B+ เหมาะกับ single-tenant/on-prem edge product และเดินมาถูกทาง แต่ควร modularize API ต่อ
Best next step แยก route groups ที่เสี่ยงสูง เช่น health, reports, line-config, backup/service และเพิ่ม smoke tests รอบ middleware boundary

4. Coding / Backend Review

4.1 จุดแข็ง

  • Raw SQL เหมาะกับระบบนี้: query analytics, time window, JSONB, category rule และ migration ต้องการ control สูง ORM จะเพิ่ม abstraction cost โดยไม่จำเป็น
  • Defensive auth patterns ดีขึ้น: มี global auth gate, role checks, internal token, auditor write-block, EULA/license gates และ admin-only sensitive operations
  • File-serving routes ระวังมากขึ้น: media/snapshot gated, filename checks, dotfile deny และ public prefixes จำกัดขึ้น
  • Upload path มี layered validation: branding upload เช็ค role, size, MIME, magic bytes, SVG rejection และ normalize ด้วย `sharp`
  • Operational commands ใช้ allowlist + `execFile`: backup/service management ลด command injection risk ได้ดี

4.2 จุดอ่อน

  • Route count สูงในไฟล์เดียว: `api-server.js` ยังมี route declarations จำนวนมาก ทำให้ review diff ยากและ route-order bug มีโอกาสเกิด
  • Helper duplication: report-worker มี copied helper logic จาก api-server บางส่วน เสี่ยง drift
  • Error handling ยังไม่ uniform ทั้งระบบ: เริ่มมี `routeError` แล้ว แต่ยังไม่ได้ migrate ครบทุก route
  • Dynamic behavior หลายจุดพึ่ง convention: เช่น internal token, worker health, report queue, camera config reload ควรมี guard/health visibility เพิ่ม

4.3 ความเห็นเชิง coding standard

สไตล์ backend เป็น pragmatic production code มากกว่า framework-heavy architecture ซึ่งเหมาะกับระบบ edge/on-prem ที่ต้อง debug ได้เร็ว จุดที่ต้องระวังคือเมื่อ feature โตขึ้น pragmatic code จะกลายเป็น accidental complexity ถ้าไม่แยก module และ test ตาม domain

5. Frontend / UI Engineering Review

5.1 จุดแข็ง

  • Vanilla JS ลด build/deployment complexity: เหมาะกับ onsite deployment ที่ต้อง debug จากไฟล์จริงและ cache-bust ง่าย
  • Feature breadth สูง: dashboard มี live events, maps, stats, reports, settings, health, LINE, audit/history และ camera management
  • i18n engine มี discipline: Thai source + English translation layer และมี gotcha/decision ชัดเรื่อง parity
  • CSP migration ทำงานหนักแล้ว: inline handlers/scripts ถูกย้ายออกจำนวนมาก ทำให้ security posture ของ SPA ดีขึ้นมาก
  • Design system มีทิศทาง: semantic tokens, SVG icons, no-emoji rule และ responsive guard ถูกบันทึกชัด

5.2 จุดอ่อน

  • `dashboard.js` ใหญ่มาก: 10k+ lines ทำให้ state coupling และ event dispatcher complexity สูง
  • ไม่มี module/lazy loading: หน้า map/report/chart หนักอาจถูกโหลดพร้อมกัน แม้ user ไม่ได้ใช้ทุกส่วน
  • ยังพึ่ง CDN สำหรับ runtime libraries: เป็นทั้ง security risk และ offline/on-prem reliability risk
  • legacy UI ยังมี carve-outs: design-token/SVG migration ยังไม่ครบทั้งหมด ซึ่งเข้าใจได้แต่ต้องคุม new code ให้เข้ม

5.3 คำแนะนำ

อย่า rewrite เป็น React/Vue เพราะชน decision และไม่คุ้ม blast radius แต่ควร split vanilla JS เป็น page/domain modules, self-host vendor libraries, lazy-load heavy map/chart/report paths และเพิ่ม UI smoke tests สำหรับ flow สำคัญ

6. Database / Data Model Review

6.1 จุดแข็ง

  • Migration discipline ดี: ใช้ `schema_migrations`, idempotent migration pattern และ fail-fast startup
  • Source-of-truth แยกชัด: camera config JSON สำหรับ configured cameras และ DB สำหรับ runtime state/history
  • Event schema รองรับหลาย vendor: ใช้ shared `events` table พร้อม `raw_json` สำหรับ vendor-specific payload
  • Snapshot columns ถูกทำให้ active: `has_snapshot` / `snapshot_filename` ช่วย query performance และลด reliance บน raw JSON
  • มี partition plan: `MANUAL_partition_events_option_a.sql` แปลว่าทีมเห็น scale bottleneck ล่วงหน้า

6.2 จุดอ่อน

  • Analytics query complexity สูง: category rules, `COUNT(DISTINCT)`, heatmap, timeline และ rollups จะหนักเมื่อ events โต
  • Partition ยัง manual: ดีที่ไม่ auto-run แต่ต้องมี threshold/checklist ที่ operator ทำตามได้
  • JSONB flexibility มีต้นทุน: raw payload ดีสำหรับ vendor variance แต่ถ้า query มากขึ้นควร promote fields ที่ใช้บ่อยเป็น column/index

7. Security Engineering Review

7.1 Controls ที่ดี

  • auth-gated media/snapshot/dashboard assets
  • CSP enforced และ inline handler cleanup จำนวนมาก
  • RBAC: admin/viewer/auditor พร้อม write-block และ admin-only routes
  • session/auth middleware enforce `must_change_password`
  • LINE webhook signature verification pattern
  • camera credential encryption helper และ health warning สำหรับ plaintext fallback
  • backup download audit และ service action audit
  • EMQX auth enabled และ dashboard localhost-only

7.2 Remaining concerns

  • Third-party JS on authenticated dashboard: ควร self-host OpenLayers/Chart.js/date adapter และ remove jsdelivr จาก CSP
  • MQTT 1883 bind all interfaces: accepted risk ได้ถ้า firewall/source restrictions ชัด แต่ต้องมี ops proof
  • Internal token high-trust: ควร fail-fast หรือ health warning ใน production เมื่อ secret missing/mismatch
  • Route security regression risk: ต้องมี automated smoke tests รอบ static/auth/admin/auditor boundary

8. Performance / Scalability Review

8.1 สิ่งที่ทำดีแล้ว

  • DB pool max และ `application_name` แยกต่อ worker
  • worker split ลด background load บน api-server
  • Puppeteer render queue กัน concurrent memory spike
  • executive summary / today counts มี cache
  • dead indexes ถูก audit และ drop แล้ว
  • snapshot thumbnail route ช่วยลด payload ใน UI

8.2 Bottleneck ที่ควรจับตา

  • Stats/category queries: จะเป็น DB bottleneck หลักเมื่อ `events` โต
  • `/api/events` pagination: `COUNT(*) OVER()`, deep `OFFSET`, `ILIKE` search มี scale limit
  • `/api/health/details`: filesystem scans และ PM2 status calls อาจหนักเมื่อ media/snapshots เยอะ
  • Frontend parse/load: dashboard monolith + CDN libs ควร split/lazy-load
  • Report queue latency: serialization ปลอดภัย แต่ต้อง expose queue length/age

9. Operations / Deployment Review

9.1 จุดแข็ง

  • PM2 ecosystem ชัด: autorestart, restart delay, max restarts และ launchd startup direction
  • Docker boundary เหมาะสม: PostgreSQL และ EMQX อยู่ Docker; app workers อยู่ PM2
  • Health endpoints มีหลายชั้น: api-server รวม worker health และ runtime diagnostics
  • Backup/restore มี script และ UI route: ดีสำหรับ onsite operator
  • Docs operations ดีมาก: `service_start.md`, `SKILL.md`, `GOTCHAS.md`, `ROADMAP.md` ช่วยลด bus factor

9.2 Gap

  • off-host backup ยังเป็น pending work
  • restore drill ควรมีหลักฐานล่าสุด
  • service health ควรแยก fast health กับ deep diagnostics
  • deployment checklist ควรรวม firewall, EMQX auth smoke, CSP smoke, backup smoke และ worker token check

10. Testing / QA Review

10.1 สิ่งที่ดี

การใช้ `node:test` แบบไม่มี dependency เพิ่มเป็นทางเลือกที่ดีสำหรับระบบนี้ เพราะรักษา deployment simplicity และทำให้ tests อยู่ใกล้ runtime จริง tests ปัจจุบันครอบคลุม crypto credentials, alert rule matching, helper error format และ color utilities ซึ่งเป็นจุดเริ่มที่ถูกต้อง

10.2 สิ่งที่ยังขาด

  • route integration tests สำหรับ auth/role gates
  • CSP header tests
  • static media/snapshot denied tests
  • migration fresh/existing schema tests
  • worker health tests
  • ingester payload replay fixtures
  • report render smoke tests แบบไม่พึ่ง customer data
  • frontend smoke tests สำหรับ login, events, health, reports, LINE settings
