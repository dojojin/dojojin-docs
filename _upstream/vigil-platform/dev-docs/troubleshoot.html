Reports / Puppeteer

Chromium อยู่ที่ report-worker แล้ว (2026-09-06)

ทั้งรายงานตามตาราง และปุ่มดาวน์โหลด PDF/PNG ด้วยมือ เรนเดอร์ใน report-worker ทั้งคู่ ผ่าน POST http://127.0.0.1:3001/render — api-server เป็นแค่ fallback เมื่อ worker ล่ม / ต่อไม่ติด / ตอบไม่ใช่ 2xx / ไม่มี INTERNAL_API_SECRET / ตั้ง REPORT_RENDER_VIA_WORKER=0

เวลาไล่ปัญหา render ให้ดู log ของ report-worker ก่อนเสมอ: pm2 logs report-worker — บรรทัดที่ขึ้นต้นด้วย [report-worker] /render บอกชื่อ fn ขนาด buffer และเวลาที่ใช้ ส่วนบรรทัด [renderViaWorker] … เรนเดอร์ในโปรเซสแทน ใน log ของ api-server แปลว่าตกลง fallback แล้ว (render ยังสำเร็จ แต่ไปกิน RAM ของ api-server)

อาการ "กดดาวน์โหลดแล้วรอนานมากแล้วค่อยได้ไฟล์" มักคือ worker กำลังยุ่งกับรายงานตามตาราง — _withPage บังคับ render ทีละหนึ่ง คำขอจึงรอจนครบ timeout 120 วินาทีก่อนตกเข้า fallback

หน้าเว็บช้า / SQL ช้า

มีสองด่านที่ log ของช้าไว้ให้แล้ว ไม่ต้องเดาว่าช้าที่ชั้นไหน — เริ่มจากด่านแรกเสมอ เพราะมันบอกได้ว่าปัญหาอยู่ฝั่ง HTTP หรือฝั่ง DB

ด่านคำสั่งอ่านอะไร
HTTP request ช้า
(api-server)		 grep '\[slow-req\]' ~/.pm2/logs/api-server-error.log | tail -50 ทุก request ที่ใช้เวลาเกิน SLOW_REQ_LOG_MS (ค่าเริ่มต้น 2000 มิลลิวินาที) จะถูก log พร้อม status, เวลาที่ใช้, method, URL, user และ IP — token/sig ใน URL ถูกปิดบังไว้แล้ว
SQL query ช้า
(Postgres)		 docker logs vigil-postgres | grep duration: Postgres เปิด log_min_duration_statement = 2s ไว้ถาวร (ตั้งผ่าน ALTER SYSTEM) ทุก statement ที่นานเกิน 2 วินาทีจะโผล่พร้อมข้อความ SQL เต็ม เอาไปวาง EXPLAIN (ANALYZE, BUFFERS) ต่อได้ทันที

ตีความ

มี [slow-req] แต่ไม่มี duration: คู่กัน → ช้าที่ฝั่ง Node ไม่ใช่ query (เช่น loop ประมวลผลแถว, JSON stringify ก้อนใหญ่, รอ HTTP ปลายทาง)

มีทั้งคู่ → ช้าที่ query จริง ไปต่อที่ EXPLAIN และดัชนี

มี duration: ที่ไม่มี [slow-req] → มาจาก worker หรืองาน background (refresher / warm job) ไม่ใช่คำขอของผู้ใช้

ขั้นตอนเต็ม + วิธีปิดชั่วคราวอยู่ใน service_start.md
