## 2. Root cause ที่พิสูจน์แล้ว

### RC-1 · `COUNT(*) OVER ()` ที่ไม่มีขอบเขตเวลา — `/api/events`

`src/routes/events.js:63` ใส่ `COUNT(*) OVER ()` เพื่อทำ `X-Total-Count` โดยคอมเมนต์เขียนไว้ว่า *"~5ms overhead"* — จริงตอนที่ events ยังเล็ก **แต่ตอนนี้มันนับทั้ง partition 5.3 ล้านแถวก่อน LIMIT จะทำงาน**

```
มี COUNT(*) OVER ()              4.08 s
ไม่มี COUNT(*) OVER ()           0.01 s     ← 400 เท่า
ไม่มี COUNT + ไม่ดึง raw_json    0.00 s
```

**นี่คือบั๊กแบบเดียวกับที่แก้ไปแล้วที่ `/api/faces`** (`82aec20`, GOTCHAS #122) — เกิดซ้ำเพราะไม่มีใครไล่หา pattern เดียวกันที่ endpoint อื่น

### RC-2 · `UPPER(lp.plate_number)` ทำให้ join ใช้ index ไม่ได้ — `/api/lpr/alerts`

`src/routes/lpr-alerts.js` join ด้วย `w.plate_number = UPPER(lp.plate_number)` → planner เลือก **Parallel Hash Join** สแกน events 4.86M × license_plates 4.6M เพื่อหาแถวที่ match แค่ 170 แถว

```
Buffers: shared hit=15,127  read=478,181   ← อ่านดิสก์ ~3.7 GB ต่อการเรียก 1 ครั้ง
```

```
join แบบเดิม (มี UPPER)     1.02 s
join ที่ใช้ index ได้        0.01 s     ← 100 เท่า
```

* ทดสอบ `SET random_page_cost = 1.1` และ `work_mem = 64MB` แล้ว **plan ไม่เปลี่ยน** (1.07 → 1.01 s เป็นผลของ cache ไม่ใช่ config) เพราะ**ไม่มี index path ให้ planner เลือกตั้งแต่แรก** → ต้องสร้าง functional index จริง
* ⚠️ **ห้ามแก้ด้วยการลบ `UPPER()` ทิ้ง** — มี **7,927 แถว** ใน `license_plates` ที่ `plate_number <> UPPER(plate_number)` (ป้ายอักษรละตินพิมพ์เล็ก) การลบ `UPPER()` จะทำให้ **แจ้งเตือนหลุด** ส่วน `lpr_watchlist` เป็นตัวพิมพ์ใหญ่ทั้ง 992 แถว

### RC-3 · postgres ยังเป็นค่า default — `shared_buffers` 128 MB บน DB 19 GB

อธิบายเลข `read=478,181` ในข้อ RC-2: cache แค่ 128 MB บนฐาน 19 GB → แทบทุก query อ่านจากดิสก์ใหม่หมด กระทบ **ทุก endpoint** ไม่ใช่ตัวใดตัวหนึ่ง

### RC-4 · `/api/appearances/search` 66.5 วินาที — พบตอนทำ harness

ไม่ได้อยู่ในรายการที่ตั้งใจวัดตอนแรก **โผล่มาตอนเขียน `scripts/perf-baseline.sh` เพราะ harness ยิงทุก endpoint ไม่เลือกที่รัก** — นี่คือเหตุผลที่ต้องมี harness เป็นไฟล์ ไม่ใช่วัดด้วยมือทีละตัวตามที่นึกออก

66.5 วินาทีแปลว่าในทางปฏิบัติ **ผู้ใช้เห็นหน้า Person Data ค้างแล้ว timeout ฝั่ง browser** — อาการเดียวกับ `/api/faces` ก่อนแก้ (51.6 s แล้วขึ้น "ไม่พบข้อมูล" ทั้งที่มีข้อมูล) `appearances` มี `COUNT(*) OVER ()` อยู่ 1 จุดด้วย

**ยังไม่ได้ EXPLAIN** → ห้ามนับเป็น root cause ที่พิสูจน์แล้ว แต่ **ต้องขึ้นเป็นงานแรกของ Phase 1** เพราะแย่กว่า `/api/events` สิบเท่า

### RC-5 · ยังไม่ได้ root-cause (ต้องทำใน Phase 1)

`/api/health/details` 1.85 s — **ยังไม่ได้ไล่หาสาเหตุ**

`/api/appearances/stats` — ตรวจแล้ว **มี in-process cache** (`_appStatsCache`): cold 5.4–6.7 วิ / warm 0.001 วิ ตัวเลขที่เห็นแกว่งเป็นเรื่อง cache ไม่ใช่ regression จาก index ที่เพิ่งเพิ่ม (ยืนยันด้วยการรัน harness ซ้ำ) · `/api/events` แกว่ง 5.8–6.4 วิ = noise band ของการวัด

### Phase 2 — สุขอนามัย index และ autovacuum (ไม่มี downtime)

**เป้า:** ลด write amplification ที่ 370k insert/วัน และไล่ dead tuple 807k ให้ทัน

#### 2A. ลบ index ที่ยังไม่มีใครใช้ — **เฉพาะที่ไม่ค้ำ constraint**

> ⚠️ **นี่ไม่ใช่ "ลบของที่ไม่ได้ใช้" แต่เป็นการแลก** — index 2 ตัวนี้รองรับ filter ที่ยังมีอยู่ในโค้ดจริง
> (`/api/events` มี `if (rule_name)` / `rule_names` และ `if (cls)` / `object_classes`)
> scan = 0 แปลว่า**ยังไม่มี operator คนไหนกดใช้ filter นั้นในอายุของ partition นี้** ไม่ได้แปลว่าโค้ดตายแล้ว
> ลบแล้ว = ประหยัดค่าเขียน 370k แถว/วัน แต่วันที่มีคนกดใช้ filter จะเจอ seq scan 5.3 ล้านแถว
> **น่าจะคุ้มที่จะแลก แต่ต้องรู้ตัวว่ากำลังแลกอะไร**

| index | ขนาด | scans |
|---|---|---|
| `events_y2026m07_rule_name_idx` | 61 MB | 0 |
| `events_y2026m07_object_class_idx` | 55 MB | 0 |

* ⚠️ **ห้ามลบ** `license_plates_pkey` (1 scan) และ `idx_plates_number_trgm` (2 scans) โดยดูตัวเลขนี้ — PK ค้ำ uniqueness ซึ่ง `pg_stat_user_indexes` ไม่นับ ส่วน trgm ใช้ตอนค้นหาแบบ fuzzy ซึ่งอาจไม่มีใครใช้ในช่วงที่นับ
* index ของ partition **เริ่มนับใหม่ทุกเดือน** → ยืนยันจากหลาย partition ก่อนตัดสินใจ
* ต้องแก้ที่ template ที่สร้าง partition ด้วย ไม่งั้นเดือนหน้ามันกลับมา

#### 2B. ตั้ง autovacuum ต่อตารางให้ดุขึ้น

```sql
ALTER TABLE events SET (autovacuum_vacuum_scale_factor = 0.02,
                        autovacuum_analyze_scale_factor = 0.01,
                        autovacuum_vacuum_cost_limit = 2000);
```
ค่า default (scale_factor 0.2) แปลว่ารอจนมี dead tuple ถึง 20% ของ 5.3 ล้านแถว = ~1 ล้านแถว ถึงจะเริ่มทำงาน

**Reproduce:** `SELECT n_dead_tup FROM pg_stat_user_tables WHERE relname='events_y2026m07'` ต้องลดลงและทรงตัว · `pg_indexes_size` ของ partition ต้องลดลงตามที่ลบ

### Phase 3 — จูน postgres (⚠️ ต้องมี downtime)

**เป้า:** ให้ working set อยู่ใน RAM แทนที่จะอ่านดิสก์ทุกครั้ง — กระทบทุก endpoint พร้อมกัน

```yaml
# docker-compose.yml — service postgres
command:
  - postgres
  - -c=shared_buffers=4GB
  - -c=effective_cache_size=11GB
  - -c=work_mem=24MB
  - -c=maintenance_work_mem=1GB
  - -c=random_page_cost=1.1
  - -c=max_parallel_workers_per_gather=4
  - -c=shared_preload_libraries=pg_stat_statements
  - -c=pg_stat_statements.max=5000
  - -c=pg_stat_statements.track=top
```

**ประเมิน downtime และความเสี่ยง:**

| ขั้น | เวลา | ความเสี่ยง |
|---|---|---|
| `docker compose up -d postgres` (recreate container) | ~30–60 วิ | volume `postgres_data` ไม่ถูกแตะ ข้อมูลไม่หาย |
| api-server + worker ทั้ง 8 ตัว reconnect | ~10–30 วิ | **migration รันตอน api-server boot — ถ้า migration พัง startup จะ abort โดยตั้งใจ** (STUBBORN_FACT #81) |
| **รวม** | **~1–2 นาที** | ระหว่างนี้ dashboard 500 · **event ที่กล้อง push เข้ามาจะหาย** (ยกเว้น LPR ที่มี spool) |

**ข้อควรทำก่อน:**
1. `pg_dump` ก่อนแตะ (19 GB → ~30–60 นาที บน NVMe)
2. ทำนอกเวลาใช้งาน
3. **เลขที่ต้องคิดให้จบก่อนแตะ ไม่ใช่ "เฝ้าดูแล้วค่อยว่ากัน":**
   `work_mem` เป็นค่า **ต่อ sort/hash node ต่อ connection** ไม่ใช่ต่อเซิร์ฟเวอร์
   - `max_connections=100` × `work_mem=24MB` × ~2 node/query ≈ **4.8 GB** ในกรณีเลวร้าย
   - `shared_buffers` 4 GB + node 8 ตัว ~2 GB + OS → บน RAM 15 GB **ยังพอ แต่ไม่เหลือเยอะ**
   - ถ้าใช้ 48 MB ตามที่คิดตอนแรก กรณีเลวร้ายจะเป็น ~9.6 GB → **เสี่ยง OOM ชัดเจน** จึงลดเหลือ 24 MB
4. ⚠️ **`max_parallel_workers_per_gather` 2→4 ไปกวน incident เดิม** — parallel query ใช้ DSM ใน `/dev/shm`
   ซึ่งเคยเต็มจน stats endpoint คืน 500 และกราฟขึ้นศูนย์ทั้งหน้า (เหตุที่ต้องตั้ง `shm_size: 1gb`)
   การเพิ่ม worker เป็น 2 เท่าคือการเพิ่มความต้องการ DSM โดยตรง → **ต้องทบทวน `shm_size` พร้อมกัน**
   หรือแยกทำทีหลังจาก `shared_buffers` เพื่อให้รู้ว่าอะไรทำให้เกิดอะไร

**Reproduce:** ยิง endpoint ชุดเดิมทั้ง 7 ตัวก่อน/หลัง · `SELECT * FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20` ต้องเริ่มมีข้อมูล

> **หลัง Phase 3 เท่านั้น** ที่เราจะเลิกเดาว่า query ไหนช้า — `pg_stat_statements` คือเครื่องมือที่ควรมีตั้งแต่แรก

**🔴 INCIDENT — migration บล็อก ingest 100 วินาที**

`DROP INDEX` บน partitioned table ต้องใช้ **ACCESS EXCLUSIVE** บน `events` · ตอนนั้น **pg_dump กลางคืนกำลังรัน** ถือ ACCESS SHARE ผ่าน `COPY public.license_plates` อยู่ → migration ขอ lock ไม่ได้ **และ lock request ที่รออยู่ไม่ได้รอเงียบ ๆ — INSERT ทุกตัวที่มาทีหลังเข้าคิวตามหลังมันด้วย**

**บทเรียน:** DDL ที่ต้องใช้ ACCESS EXCLUSIVE **ห้ามอยู่ในไฟล์ migration** เพราะ migration รันตอน api-server boot ซึ่งเป็นจังหวะที่ไม่มีใครเฝ้า และ failure ที่นั่น abort startup โดยตั้งใจ (STUBBORN_FACT #81) → ย้ายออกไปรันมือพร้อม `lock_timeout` ที่ล้มเร็วแทนที่จะเข้าคิว · **เสนอเพิ่มเป็นบรรทัดใน GOTCHAS (รอไฟเขียว)**

### Phase 0.5 — ผลการทดลอง 2026-07-31 (ยังไม่ลงมือ)

**❌ แผนเดิม "เอา `event_time` ไปไว้บน `appearances` เพื่อให้ prune partition" — ใช้ไม่ได้ พิสูจน์แล้ว**

ทดสอบบน temp copy (ไม่แตะตารางจริง) พร้อม twin clause จริงทุกแบบ:

| แบบ | เวลา | plan |
|---|---|---|
| เดิม: join ด้วย `id` อย่างเดียว | 5.48 s | Merge Join |
| ใหม่: join ด้วย `id` + `event_time` | 5.54 s | Merge Join |
| ใหม่ + `random_page_cost=1.1` | 5.56 s | Merge Join |
| ใหม่ + บังคับ nested loop | **6.18 s** | Nested Loop |

planner มอง `e.event_time = a.ev_time` เป็นแค่ **Join Filter** ไม่ใช่เงื่อนไข prune
> ระหว่างทางเคยวัดได้ 0.78 s แล้วเกือบสรุปว่าสำเร็จ — **ตัวเลขนั้นหลอกเพราะเผลอตัด twin clause ออกจากเทสต์** วัดใหม่แบบ apples-to-apples แล้วเท่าเดิม

**ต้นทุนจริงกระจายแบบนี้ (วัดแยกทีละส่วน):**
```
join appearances × events         0.42 s
twin EXISTS แกนหลัก               ~4.1 s   ← ตัวการจริง
  + inner JOIN appearances a2      ~0.9 s
รวม                               5.41 s
```
twin แพงเพราะเงื่อนไข**แถวนอก**ต้องอ่าน `e.raw_json->'data'->'Object'->>'ObjectID'` = **detoast jsonb ~2.5 KB ทั้งก้อน 33,221 ครั้ง เพื่อเทียบ string เดียว** · และเหตุผลเดียวที่ต้อง join `events` ก็เพื่อเอา `event_type` กับฟิลด์นั้น

**✅ แบบใหม่ที่วัดแล้วได้ผล: ย้าย `event_type` + `event_time` + ObjectID ของ twin มาไว้บน `appearances`**

```
COUNT ของจริงตอนนี้    5.42 s
COUNT แบบใหม่           1.33 s   ← ไม่ต้อง join events เลย · ผลลัพธ์ตรงกันเป๊ะ (273,297)
หน้าเพจ LIMIT 50        0.00 s
```

**สิ่งที่ต้องแลก — ต้องให้เจ้าของตัดสิน:**
- เพิ่ม 3 คอลัมน์ + index · **backfill 300,366 แถว**
- **แตะ ingest 6 จุดใน 3 ไฟล์** (`mqtt-subscriber.js` ×2, `hikvision-isapi.js` ×3, `dahua-cgi.js` ×1) — พลาดจุดใดจุดหนึ่ง แถวใหม่จะประเมิน twin ผิด
- ⚠️ **ต่างจากที่เคยปฏิเสธไปตรงไหน:** ตอนคุยเรื่อง "ติดธง twin ตอน ingest" เราเลือกไม่ทำเพราะแลก *"ช้าแต่ถูกเสมอ"* เป็น *"เร็วแต่ผิดถาวรได้"* · แบบนี้**เก็บแค่ input ไม่ได้เก็บคำตัดสิน** — กฎ twin ยังคำนวณสดทุกครั้ง ถ้าคอลัมน์ผิดก็แค่แถวนั้นเพี้ยน และ **สร้างใหม่จาก `events` ได้ตลอดเวลา** ไม่มีเคส "ผีค้างถาวร"
