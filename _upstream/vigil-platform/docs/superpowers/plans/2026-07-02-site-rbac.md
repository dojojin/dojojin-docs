# Per-Site Access Control (Site-Scoped Viewer) — Design + Plan

> Status: **PLANNED 2026-07-02**. Goal: site users (VSS / BMA / Phuket) = **viewer that
> can ACT (ack + comment on face & LPR) but NOT change settings**, and only see/act on
> **their own site's data**. Central (main) admins keep full cross-site access.
> P2/P3 are security-critical → implement **Advisor-led**, per-cluster, with tests.

---

## 1. Current state (verified 2026-07-02)

**Roles (exist):** `admin` (full), `auditor` (read-all, global write-block), `viewer`.
**Sites:** main(Central) · vss · bma · phuket. Cameras today: main 5, vss 7 (bma/phuket empty).
**Users today:** admin · gyan/asarn (auditor) · vss (viewer). The `vss` viewer has **NO
user_sites rows → currently sees ALL sites (fail-open)** — the exact hole to close.

**Infra already present:**
- `user_sites(user_id, site_id)` M2M (migration 054). **But no write endpoint / no UI to assign.**
- `cameras.site_id` direct. Other data (events, license_plates, appearances, face events)
  derives site via **`camera_id → cameras.site_id`**. Direct site_id also on
  camera_groups, report_schedules, edge_status.
- Config writes: **fully admin-gated** — `requireAdminForWrites` on /cameras /groups
  /alert-rules /line-config /map /categories /settings /report-schedules /license
  /alert-logs; explicit `requireAdmin` on /users /sites /branding /eula. Global auditor
  write-block rejects all non-GET from auditor. **→ viewer already cannot write config.**
- `user_sites` enforced in **ONE place only**: `GET /api/cameras` (cameras.js:408, fail-open).

**⇒ The role/write-block layer is DONE. The missing layer is SITE SCOPING (read + act).**

## 2. Design

**No new role.** "Site viewer" = `viewer` role **+ user_sites assignment**:
```
admin                     → all sites · write config
auditor                   → all sites · read-only
viewer + user_sites = ∅   → (fail-open policy — see decision D2)
viewer + user_sites = {VSS} → sees/acts ONLY on VSS · no config     ← the target
```
- **Read scope:** every site-bound read filters to the user's sites. Camera-derived tables
  join `cameras c ON c.id = <table>.camera_id WHERE c.site_id = ANY($allowed)`.
- **Act scope:** ack/comment verifies the target event's `camera_id → site_id ∈ allowed`
  before writing (stops a VSS viewer acking a Phuket case).
- **admin/auditor bypass:** `allowedSites = ALL` (sentinel) → no filter injected.
- **Global (not per-site) data stays global:** watchlist plates/groups, LPR gates,
  vehicle-types, categories, mismatch-dismiss — platform-wide config (admin writes;
  viewers may read the reference list). Only the **hits/alerts** derived from events are
  site-scoped.

## Open decisions (P0)

- **D1 — health scope:** does a scoped viewer see ALL sites' health or only theirs?
  Recommend **only theirs** (consistent RBAC); confirm (ops may want full view).
- **D2 — fail-open policy:** ✅ **DECIDED 2026-07-02 — fail-closed.** viewer with no
  user_sites rows = sees NOTHING (siteWhere returns AND FALSE). admin/auditor = ALL (null sentinel).
  Operators MUST assign user_sites before enabling scoped viewers (P5 UI does this; until then
  use direct INSERT). Initial assignment: vss user → VSS site (INSERT executed 2026-07-02).
- **D3 — global data read:** confirm viewers MAY read global reference lists (watchlist
  plates, gates, vehicle-types) — only hits/events are site-scoped.

## Notes
- **P2/P3 = Advisor-led.** Central helper `siteWhere()` keeps it consistent; a per-endpoint
  hand-rolled filter risks a missed clause = cross-site leak. Test each cluster.
- **PDPA:** face/plate/appearance = personal data; site-scoping is a real minimization boundary.
- Consider **app-layer now, Postgres RLS later** (Tier-2, `project_multisite_camera_sites`)
  as defence-in-depth once app-layer is proven.
