## 2. ⚠️ แก้ความเข้าใจผิดของตัวเอง — "ยิ่งรอยิ่งแพง" **ไม่จริง**

ผมเคยบอกว่าต้องรีบทำเพราะตารางจะโตจาก 2.2 GB เป็น ~25 GB ในอีกปี ซึ่ง**ผิด** —
ข้อนั้นจริงเฉพาะกับวิธี **copy ข้อมูลไปตารางใหม่** แต่วิธีที่ควรใช้จริงคือ **ATTACH**
ซึ่ง**ไม่ copy อะไรเลย** ขนาดตารางจึงแทบไม่มีผลต่อต้นทุนการย้าย

**เหตุผลที่ควรทำเร็วคืออีกเรื่องหนึ่ง และแรงกว่า:**

> ตอน ATTACH ตารางเดิมทั้งก้อนจะกลายเป็น **partition เดียว** ที่ลบแยกไม่ได้
> ทุกเดือนที่รอ = อีกหนึ่งเดือนที่ถูกหลอมติดอยู่ใน partition ก้อนแรกนั้นถาวร
>
> ทำวันนี้ → partition ก้อนแรกมี 1 เดือน · เดือนถัด ๆ ไปแยกกันสวยงาม
> รอถึง ก.ค. 2027 → partition ก้อนแรกมี 12 เดือน **ลบทีละเดือนไม่ได้ ต้อง DELETE เหมือนเดิม**
> ซึ่งคือปัญหาที่ P5.2 ตั้งใจจะแก้ตั้งแต่แรก

## 3. การออกแบบ — ATTACH ไม่ใช่ copy

### ทำไมถึงไม่ต้อง copy

PostgreSQL แปลงตารางธรรมดาเป็น partitioned ในที่เดิมไม่ได้ แต่ทำแบบนี้ได้:
เปลี่ยนชื่อตารางเดิม → สร้าง parent ใหม่ที่เป็น partitioned → **ATTACH ตารางเดิมเข้าไปเป็น partition แรก**
ข้อมูล 5.3M แถวอยู่ที่เดิมทั้งหมด ไม่ถูกเขียนใหม่แม้แต่แถวเดียว

### ต้นทุนจริง (วัดแล้วบนตารางจริง)

| ขั้น | lock ที่ต้องใช้ | เวลาที่วัดได้ |
|---|---|---|
| `ADD CONSTRAINT … NOT VALID` | ACCESS EXCLUSIVE (metadata) | **ขอ lock ได้ในครั้งที่ 2 · 1.9 วิ** |
| `VALIDATE CONSTRAINT` | SHARE UPDATE EXCLUSIVE — **ไม่บล็อก INSERT** | **0.5 วิ** (5.32M แถว) |
| `DROP CONSTRAINT` | ACCESS EXCLUSIVE | **0.00 วิ** |

> 🔬 **สิ่งที่เจอตอนวัด และเป็นข้อสำคัญที่สุดของแผนนี้**
> ครั้งแรกที่ลองด้วย `lock_timeout='3s'` **ขอ lock ไม่ได้เลย** — ตารางนี้มี INSERT ~5 ครั้ง/วินาที
> ตลอดเวลา จึงแทบไม่มีช่องว่าง · ต้องใช้ **retry loop ที่ `lock_timeout` สั้น** (1 วิ) แล้วลองใหม่
> จนกว่าจะเจอช่อง — ได้ในครั้งที่ 2
>
> **ห้ามใช้ lock_timeout ยาวหรือไม่ตั้งเลยเด็ดขาด** — DDL ที่รอ lock จะลาก INSERT ทุกตัวเข้าคิว
> ตามหลัง (GOTCHAS #134 — เคยทำ ingest หยุด 100 วินาทีมาแล้ว)

### เรื่อง PRIMARY KEY

parent ที่เป็น partitioned ต้องมี PK ที่**รวมคอลัมน์ที่ใช้แบ่ง partition** แต่ตารางเดิมมี
`PRIMARY KEY (id)` เฉย ๆ → ATTACH ไม่ผ่านถ้า parent ประกาศ PK

**ทางออก: parent ไม่ต้องมี PK เลย** ปลอดภัยเพราะตรวจแล้วว่า:

| ตรวจอะไร | ผล |
|---|---|
| FK ที่ชี้มาที่ `license_plates` | **ไม่มีเลย** |
| โค้ดอ้าง `lp.id` / `license_plates.id` | **จุดเดียว** — `lpr-query.js:367` `lp.id IS NULL` (เป็น anti-join ใช้คอลัมน์อะไรก็ได้) |
| `ON CONFLICT` บน license_plates | **ไม่มีเลย** |

แต่ละ partition ยังเก็บ PK ของตัวเองไว้ได้ตามเดิม — เสียแค่การรับประกัน uniqueness **ข้าม** partition
ซึ่งไม่มีใครพึ่งพา

## 4. ขั้นตอน

```sql
-- 0) เลือกขอบเขตของ partition ก้อนแรก (ดูข้อ 5 เรื่องเวลา)
--    ต้องครอบข้อมูลที่มีอยู่ + ที่จะ insert เข้ามาระหว่างทำ
-- 1) พิสูจน์ให้ postgres รู้ว่าทุกแถวอยู่ในขอบเขตนั้น (ATTACH จะได้ไม่ต้อง scan ซ้ำ)
ALTER TABLE license_plates ADD CONSTRAINT lp_range_ck
  CHECK (detected_at >= '2026-07-01' AND detected_at < 'BOUNDARY') NOT VALID;   -- retry loop
ALTER TABLE license_plates VALIDATE CONSTRAINT lp_range_ck;                      -- 0.5 วิ ไม่บล็อก

-- 2) สลับชื่อ + สร้าง parent + ATTACH  (ทำในทรานแซกชันเดียว, lock_timeout สั้น)
BEGIN;
  ALTER TABLE license_plates RENAME TO license_plates_y2026m07;
  CREATE TABLE license_plates (LIKE license_plates_y2026m07 INCLUDING DEFAULTS
                               INCLUDING GENERATED INCLUDING IDENTITY)
    PARTITION BY RANGE (detected_at);
  ALTER TABLE license_plates ATTACH PARTITION license_plates_y2026m07
    FOR VALUES FROM ('2026-07-01') TO ('BOUNDARY');
COMMIT;

-- 3) สร้าง partition ล่วงหน้า + index บน parent (แบบเดียวกับ migration 103)
CREATE TABLE license_plates_y2026m08 PARTITION OF license_plates
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
-- … ล่วงหน้าถึง 2027-12 เหมือนที่ events ทำ
CREATE INDEX ON ONLY license_plates (…);   -- แล้ว ATTACH index ของแต่ละ partition
```

**สิ่งที่ต้องทำในการเปลี่ยนแปลงเดียวกัน — ห้ามแยก**

`lpr-retention.js` ต้องเลิกใช้ `DELETE FROM license_plates WHERE event_id = ANY(...)`
แล้วไปใช้ DROP PARTITION แทน (ใช้ `helpers/partitionRetention.js` ที่ทำไว้แล้วใน P5.1 ได้เลย
เพียงขยายให้รู้จักตารางที่สอง) — **ถ้า rewrite แล้วยังลบแบบเดิม = เสียค่าย้ายฟรี ๆ**

## 5. ⏰ เรื่องเวลา — จุดที่พลาดง่ายที่สุด

วันนี้คือ **2026-07-31** ข้อมูลทั้งหมดอยู่ในเดือน ก.ค. เดือนเดียว **แต่เที่ยงคืนนี้จะมีแถวเดือน ส.ค. เข้ามา**

| ทำเมื่อไหร่ | ขอบเขต partition แรก | ผล |
|---|---|---|
| **ก่อนเที่ยงคืนวันนี้** | `'2026-07-01' → '2026-08-01'` | สะอาดที่สุด · partition แรกมี 1 เดือนพอดี |
| หลังเที่ยงคืน | `'2026-07-01' → '2026-09-01'` | ต้องกินไป 2 เดือน เพราะ CHECK เดือนเดียวจะไม่จริงแล้ว |
| **ทางที่ทนต่อเวลา (แนะนำ)** | ตั้งขอบเขตเป็น**อนาคต** เช่น `'2026-09-01'` | CHECK ยังจริงเสมอไม่ว่าจะทำตอนไหน · แลกกับ partition แรกกิน 2 เดือน |

> ข้อควรระวัง: ระหว่างขั้น 1 กับขั้น 2 ยังมีแถวใหม่ไหลเข้าตลอด **ขอบเขตต้องเป็นอนาคต**
> ไม่งั้น CHECK ที่ validate ผ่านตอน 20:30 อาจไม่จริงแล้วตอน 20:31

## 6. ความเสี่ยงและการถอย

| ความเสี่ยง | ระดับ | การรับมือ |
|---|---|---|
| ขอ ACCESS EXCLUSIVE ไม่ได้ | **สูง — เกิดจริงตอนทดสอบ** | retry loop `lock_timeout='1s'` · ห้ามรอ lock ยาว (GOTCHAS #134) |
| ทำครึ่งทางแล้วค้าง | ต่ำ | ขั้น 2 อยู่ในทรานแซกชันเดียว — ล้มก็ ROLLBACK ทั้งชุด ตารางเดิมยังชื่อเดิม |
| เสีย PK ข้าม partition | ต่ำ | ตรวจแล้ว ไม่มี FK · ไม่มี ON CONFLICT · โค้ดอ้าง `id` จุดเดียวและไม่ต้องการ uniqueness |
| index หายตอนสร้าง parent | ปานกลาง | ตารางเดิมเก็บ index ของตัวเองครบ · parent ต้องสร้างใหม่ให้ partition ในอนาคต **ตรวจ `\\d` ก่อน-หลัง** |
| แถวหลุดไประหว่างสลับ | ต่ำ | นับ `count(*)` ก่อน-หลังในทรานแซกชันเดียวกัน |

**การถอยหลังทำเสร็จแล้ว:** `DETACH PARTITION` แล้ว rename กลับ — ข้อมูลไม่เคยถูกย้าย
จึงถอยได้เต็มรูปแบบ ไม่มีการสูญเสีย

## 7. สิ่งที่ต้อง verify หลังทำ (Reproduce ตาม WA #3)

1. `count(*)` ก่อน-หลัง เท่ากันเป๊ะ
2. INSERT แถวใหม่แล้วไปลงถูก partition (`tableoid::regclass`)
3. `EXPLAIN` ของ query ที่กรองช่วงเวลา ต้องเห็น **partition pruning** (`Subplans Removed`)
4. `/api/lpr/stats` · `/api/lpr` · หน้า LPR ทั้งหมดยังทำงาน — โดยเฉพาะ `lpr-query.js:367` ที่ใช้ `lp.id IS NULL`
5. ingest ไม่สะดุด — นับ plate ต่อนาทีคร่อมช่วงที่ทำ เทียบกับก่อนหน้า
6. `pruneLprRows` ที่แก้ใหม่ยังลบของเก่าได้ (ทดสอบกับ partition สังเคราะห์ เหมือนที่ทำใน P5.1)

## 8. สรุปสำหรับตัดสินใจ

**ต้นทุน:** วินาที ไม่ใช่นาที · ไม่ต้อง copy ข้อมูล · ถอยได้เต็มรูปแบบ · ไม่ต้องหยุดระบบ
**ความเสี่ยงหลักข้อเดียว:** จังหวะขอ lock บนตารางที่มี INSERT ตลอดเวลา — แก้ด้วย retry ที่ timeout สั้น
**ถ้าไม่ทำ:** ทุกเดือนที่ผ่านไปถูกหลอมเข้า partition ก้อนแรกที่ลบแยกไม่ได้ถาวร

**ยังไม่ด่วนในแง่ประสิทธิภาพ** — `lpr_retention_days = 365` แปลว่า DELETE ก้อนใหญ่จะยังไม่เกิดจนถึง
ก.ค. 2027 เหมือน P5.1 · แต่ **ยิ่งทำเร็วยิ่งได้ partition ที่ลบแยกได้มากเดือน**

## 9. ❌ ทำแล้วถอย — บทเรียนที่แพงที่สุดของแผนนี้

**การย้ายสำเร็จทุกอย่างตามที่วางไว้** — DDL 1 วินาที · ingest ไม่หยุด · index ไม่ถูกสร้างซ้ำ ·
routing/pruning/DROP PARTITION ทำงานครบ · `ANALYZE` parent แก้ปัญหา planner ที่เจอตอน verify

**แต่ 3 ชั่วโมงต่อมาพบว่า `/api/lpr/alerts` ใช้เวลา 9 วินาที** (เดิม ~0.02s)

ทดสอบชี้ขาด — query เดียวกัน คอลัมน์เดียวกัน ต่างแค่ตารางที่ join:

| | เวลา |
|---|---|
| `license_plates` (parent หลัง partition) | **8.63s** |
| `license_plates_y2026m07` (partition เดียว = สภาพก่อน) | **0.02s** |

**ช้าลง 430 เท่า**

### ต้นเหตุ

`events` แบ่งตาม `event_time` · `license_plates` แบ่งตาม `detected_at` · **แต่ join กันด้วย `event_id`**
→ partition-wise join เป็นไปไม่ได้ · planner เลิกใช้ index `UPPER(plate_number)` แล้วเลือก
**Merge Join ทั้ง 5.76 ล้านแถวเพื่อหา 175 รายการ** (อ่าน buffer 8.8 ล้านครั้ง)
ตอนเป็นตารางเดียว มันขับจาก `lpr_watchlist` 456 แถวผ่าน index ได้เลย

**ตัดตัวแปรอื่นออกครบแล้ว:** index บน parent ครบ 10 ตัว `indisvalid=true` children 18 ·
`ANALYZE lpr_watchlist` ไม่ช่วย · hit จริงมีแค่ 175 · ใส่กรอบเวลา 30 วันทั้งสองฝั่งยังได้ 3.9s ·
เขียน query ใหม่ให้ขับจาก watchlist ยังได้ 6.8s

### สิ่งที่ผมพลาดในการวางแผน

แผนนี้ระบุความเสี่ยงหลักไว้ว่าคือ **จังหวะขอ lock** ซึ่งผ่านฉลุยทั้งสองครั้ง
ความเสี่ยงจริงคือ **plan ของ query ที่ join ข้ามตารางที่ partition คนละคีย์** ซึ่ง
**ตอนซ้อมกับตารางจำลอง ผมซ้อมแค่ routing / pruning / DROP PARTITION — ไม่ได้ซ้อม query จริงของ endpoint เลย**

### การถอย (2026-08-01)

`DETACH PARTITION` → ปลด CHECK → ย้ายแถวเดือน 8 กลับ → rename สลับ → ลบ shell
**7.4 วินาที · ไม่มีข้อมูลสูญหาย** (ตรวจ 0 แถวที่มีเฉพาะใน shell ก่อนลบ) · `/api/lpr/alerts` กลับมา **0.007-0.012s**

> ⚠️ รอบแรกที่ถอยล้มเหลวเพราะ CHECK `lp_range_ck` ยังจำกัดไว้แค่เดือน 7 ทำให้ insert
> แถวเดือน 8 กลับไม่ได้ — **ล้มแบบ atomic ไม่มีอะไรเปลี่ยน** ต้องปลด constraint ก่อนย้ายกลับ

### เงื่อนไขก่อนจะลองใหม่

1. **แก้ query ของ `/api/lpr/alerts` ให้เร็วบนตารางที่ partition แล้วก่อน** แล้วพิสูจน์ด้วยการวัด
2. หรือเปลี่ยนคีย์ partition ให้ตรงกับที่ join จริง (แต่ `event_id` ไม่ใช่คีย์เวลา — ทำไม่ได้ตรง ๆ)
3. **ซ้อมด้วย query จริงของ endpoint ทุกตัวที่แตะตารางนั้น ไม่ใช่แค่ routing/pruning**
