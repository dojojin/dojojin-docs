Design Spec · Vigil Platform · Draft 2026-07-29

Vigil เป็น Hub ให้ CIB — เลิก forward กล้อง เปลี่ยนเป็นรับ/ส่งข้อมูลแทนกล้อง

วันนี้กล้อง ANPR ที่ site hkt push ภาพ+metadata ตรงไปยัง CIB โดยตรง (ทุก field รวมถึง helmet/rider/seatbelt ที่กล้องตรวจจับเอง) แผนนี้ออกแบบให้ Vigil เป็นคนกลาง — รับข้อมูล จากกล้องแทน CIB แล้วส่งต่อเฉพาะ field ที่อนุญาต (ป้ายทะเบียน + ภาพ) ให้ CIB เหมือนเดิม พร้อม buffer ให้เมื่อ network ของ CIB ขาดช่วง

แก้ความเข้าใจก่อนเริ่ม — ทิศทางคือ Push ไม่ใช่ Pull

หลักฐาน 3 จุดที่ตรวจสอบมาแล้วยืนยันตรงกัน: กล้อง เป็นฝ่าย push ออก ไปหา CIB (ไม่ใช่ CIB ดึงจากกล้อง) — uploadTimeConsuming บนกล้องแสดง uploadType: ISAPIListen กำลัง Uploading จริง (718,458/722,170 สำเร็จ); httpHosts slot 1 ของกล้องตั้งเป็น push target ไปที่ receive_hik_phuget; และ lpr-forward.js ที่มีอยู่แล้ว ในระบบเขียนไว้ตรงๆ ว่า "the LPR camera has ONE push slot" — คำว่า "ดึง" ที่ใช้คุยกันน่าจะหมายถึง "CIB ได้ข้อมูลจากกล้อง" แบบภาษาพูด ไม่ใช่ pull ทางเทคนิค เอกสารนี้ออกแบบบนฐาน push เป็นหลัก และเก็บ pull-based API ไว้เป็นเป้าหมายปลายทาง (Phase 6)

สถานะปัจจุบัน

GATE

สิ่งที่ต้องได้คำตอบจาก CIB ก่อนฟันธง feasibility — ไม่ใช่สิ่งที่เราตรวจเองได้

เมื่อ Vigil ตัดฟิลด์ (helmet/rider/seatbelt) ออกจาก payload ก่อนส่งต่อ payload จะไม่ใช่ byte เดิมที่กล้องเคยส่งอีกต่อไป — ต้องถามฝั่ง CIB ว่า parser ของเขา tolerate field ที่หายไปได้ไหม (เช่น XML schema validation เข้มงวดจนพัง หรือรับแบบ loose parsing) และถามคู่กันว่า ฝั่งเขารับได้แค่ inbound POST อย่างเดียว หรือ poll endpoint ที่เราเปิดให้ได้ด้วย — คำตอบข้อหลังเป็นตัวตัดสินว่า Phase 6 (pull API) จะทำได้จริงหรือต้องค้างที่ push-emulation ตลอดไป ทุก phase ด้านล่างออกแบบให้เดินหน้าได้โดยไม่ต้องรอคำตอบนี้ก่อน แต่ต้องรู้คำตอบก่อน "cutover" จริงใน Phase 2 — ข้อนี้สำคัญขึ้นอีกเมื่อ Edge เป็นคน emit เอง (2026-07-29): push (Edge ส่งออก, ต้องการแค่ outbound) กับ pull (CIB มา poll Edge, ต้องการ inbound reachability เข้า Edge) มีข้อกำหนดด้าน network คนละชุดกันโดยสิ้นเชิง — 2nd uplink ที่วางแผนไว้ (ดูหัวข้อถัดไป) แก้ปัญหาแค่ฝั่ง outbound เท่านั้น ถ้าคำตอบจาก CIB คือ pull ต้องออกแบบ inbound path แยกต่างหาก (เช่น เปิดผ่าน Cloudflare Tunnel เดิม) ไม่ใช่ผ่าน uplink ใหม่นี้

Field Scoping — Allowlist ไม่ใช่ Denylist

ใช้หลักการเดียวกับ v_*_public views ที่มีอยู่แล้วใน docs/REF_third-party-integration.md (exclude PII/credential column) แต่กลับด้าน: ประกาศเฉพาะ field ที่อนุญาตส่งออก (allowlist) แทนการ list field ที่ห้าม — เหตุผล: ถ้ากล้อง อัป firmware แล้วเพิ่ม field ตรวจจับใหม่ (violation ชนิดใหม่) denylist จะไม่รู้จักและหลุดออกไปเอง โดยไม่มีใครสังเกต ส่วน allowlist จะตัดค่าที่ไม่รู้จักทิ้งเป็นค่าเริ่มต้นเสมอ

Emitter + Network Path — 2 การตัดสินใจที่แยกจากกัน

ฉบับร่างก่อนหน้านี้รวม "ใคร emit" กับ "ผ่าน network ทางไหน" เป็นเรื่องเดียวกัน — จริงๆ เป็นคนละแกน Emitter = Edge (เจ้าของตัดสินใจแล้ว 2026-07-29 — ไม่ทบทวนซ้ำ) ส่วน Path ยังมี 2 สถานะ ที่ต้องวางแผนแยกกัน: ผ่าน Fortigate เดิม (วันนี้, ยังบล็อก) กับผ่าน uplink ที่ 2 โดยเฉพาะ (เป้าหมาย ระยะยาว ไม่ผ่าน Fortigate เลย)

Path วันนี้ — ผ่าน Fortigate เดิม

Edge → CIB ผ่าน enp0s31f6 (10.0.10.254)

egress 1.10.144.84 ยังโดน 403 — ต้องรอ ask #3 (hkt-firewall-request-2) ผ่านก่อนถึงจะใช้ path นี้ได้จริง ยังไม่ยกเลิกคำขอนี้ (ดูคำแนะนำด้านล่าง)

Path เป้าหมาย — uplink ที่ 2 เฉพาะ

Edge → CIB ผ่าน internet คนละเส้นทาง ไม่ผ่าน Fortigate

ตัดปัญหา Fortigate/ask ออกทั้งหมดในระยะยาว — ต้องมี phase แยกสำหรับ policy routing (ดู Phase 5 ด้านล่าง) เพราะ box นี้มี NIC เดียวจริงในตอนนี้ (ตรวจแล้วผ่าน ip -br link บน sshhkt: มีแค่ enp0s31f6 + tailscale0) — ต้องหา uplink ใหม่ (USB-NIC / LTE modem / เส้นทางอื่น) มาต่อเพิ่มก่อน ไม่ใช่ของที่มีอยู่แล้ว

คำแนะนำ: อย่าถอน ask #3 — เก็บไว้เป็น path ชั่วคราวให้ Phase 1–4 เดินหน้าได้ระหว่างรอจัดหา uplink ที่ 2 (เป็นเรื่องฮาร์ดแวร์/สัญญาใหม่ ใช้เวลาแน่นอน) ถ้าถอนแปลว่า Phase 2 (cutover) ต้องรอ อุปกรณ์มาก่อน ไม่ใช่แค่รอ policy อนุมัติ — เป็นทางเลือกของเจ้าของ แต่ควรรู้ต้นทุนเวลาที่ต่างกัน

Phases

1

Shadow / Dual-run

พิสูจน์ parity ก่อน ไม่แตะฟีดจริง

กล้องยัง push ไป CIB ตามเดิมทุกอย่าง (slot 1 ไม่แตะ) — ถ้ากล้องมี httpHost slot 2 ว่าง (ต้องตรวจสอบความจุจริงก่อน ยังไม่ยืนยัน) ให้ตั้ง slot 2 push สำเนาเข้า Vigil ด้วย Vigil parse ตัด field ตาม allowlist แล้ว emit ไปยัง staging target เท่านั้น (ไม่ใช่ CIB จริง) แล้ว diff กับสิ่งที่ CIB ได้รับจริง (log ฝั่งกล้องหรือฝั่ง CIB ถ้าขอดูได้) ทีละ record เพื่อยืนยันว่า field allowlist ครบและไม่มีอะไรหลุด

Rollback: ปิด slot 2 อย่างเดียว — slot 1 (CIB จริง) ไม่ถูกแตะเลยตลอด phase นี้
2

Cutover — กล้องตัวเดียว

เปลี่ยนจริงครั้งแรก

เมื่อ parity ผ่านใน Phase 1 และได้คำตอบจาก CIB เรื่อง gate (tolerate field หายได้) แล้ว — เลือกกล้อง 1 ตัว repoint slot 1 จาก CIB ตรง ให้มาที่ Vigil edge แทน (emitter = Edge เดินผ่าน Fortigate เดิมไปก่อน ตาม ask #3) Edge รับ raw push, ตัด field, ส่งต่อ payload ที่ redact แล้วไปยัง CIB จริง (endpoint เดิม receive_hik_phuget) กล้องมองไม่เห็นความต่าง — จบด้วย Edge เป็นคนกลางจริง (ยังไม่ผ่าน uplink ที่ 2 — ตามหลังใน Phase 5)

Rollback: บันทึกค่า slot 1 เดิม (IP/port/path) ของกล้องตัวนี้ไว้ก่อนแตะ — ถ้า CIB รายงานว่าข้อมูลขาด/ผิดปกติ ยิง ISAPI PUT คืนค่าเดิมได้ทันที ไม่ต้อง restart อะไรฝั่งกล้อง
3

Buffering

ประโยชน์หลักที่เจ้าของต้องการ

ใช้ lpr-forward.js ที่มีอยู่แล้ว (spool ลงดิสก์เมื่อส่งไม่สำเร็จ, drain timer retry, expiry แบบ log ดัง ไม่เงียบหาย, self-check ในตัว) ไม่ต้องเขียนกลไก spool ใหม่ — แต่ค่า default ปัจจุบัน maxAgeMs = 3,600,000 (1 ชั่วโมง) สั้นเกินไปสำหรับ "CIB network ขาดแล้วมา backfill" ตามที่ต้องการ ต้องปรับ (เช่น 24–72 ชม.) และคิดเรื่องขอบเขตดิสก์ (กี่ record/วัน × กี่วันสำรอง ก่อน disk เต็ม) ให้ชัดก่อนใช้จริง

Rollback: ไม่มีการเปลี่ยน topology ใน phase นี้ ปรับแค่ config ตัวเลข — ย้อนกลับคือแก้ค่ากลับ
4

Fleet rollout

ครบ 4 กล้อง site hkt

ทำซ้ำ Phase 2 ทีละกล้องจนครบทั้ง 4 ตัว (C28-KAT-SB-15, 10.5.100.9, 10.9.100.2, 10.5.100.17) — ทีละตัว ไม่ทำพร้อมกันทั้งชุด เพื่อให้ยังมี rollback point ทีละจุดถ้าตัวใดตัวหนึ่งมีปัญหา ไม่กระทบตัวอื่นที่ cutover ไปแล้ว

Rollback: per-camera เหมือน Phase 2 — เก็บ log ว่าตัวไหน cutover แล้วบ้าง
5

Uplink ที่ 2 + Policy Routing

เลิกพึ่ง Fortigate ระยะยาว

จัดหา uplink ใหม่ (USB-NIC ต่อ LTE modem หรือเส้นทาง internet อื่นที่ไม่ผ่าน Fortigate 10.0.10.254) ต่อเข้า Edge box (ปัจจุบันมี NIC เดียวจริง — ตรวจแล้ว) จากนั้นตั้ง policy routing แบบ source/destination-specific ให้เฉพาะ traffic ที่ปลายทางเป็น 202.124.201.106:10001 ออกทาง uplink ใหม่เท่านั้น — ไม่แตะ default route เดิม ที่ยัง carry flow อื่นของ Edge อยู่ (Cloudflare Tunnel UDP 7844 — เอกสาร firewall เดิมเขียนไว้ว่า "ห้ามปิด" เพราะเป็นทางเข้าเดียวจากภายนอก, และ Tailscale ที่เป็นทางสำรอง) เมื่อ uplink พร้อมแล้ว ต้องทดสอบ empty-POST ไปยัง CIB ผ่าน uplink ใหม่ก่อนใช้งานจริง — ผลที่เป็นไปได้ 2 แบบ: 200 = ผ่านทั้ง 2 ชั้น (Fortigate เดิมไม่เกี่ยวแล้ว), 403 = แปลว่า CIB เองก็มี IP allowlist แยกต่างหาก ต้องขอเพิ่ม IP ใหม่กับ CIB โดยตรง ไม่ใช่ปัญหา Fortigate อีกต่อไป

Rollback: ทดสอบ verify flow 2 (Cloudflare Tunnel) และ flow 3 (Tailscale) ว่ายังผ่านปกติ ทั้งก่อนและหลัง ตั้ง policy routing — ถ้าพลาดแล้ว default route ถูกแก้ผิดจุด จะเสียทั้ง tunnel และ Tailscale พร้อมกันบนเครื่องที่อยู่ไกลคนละจังหวัด ต้องมีคนหน้างานช่วยได้ก่อนทำจริง
6

Pull API (เป้าหมายปลายทาง)

ต้องได้คำตอบจาก gate ก่อน

ถ้า CIB ยืนยันว่ารับ poll แทน inbound POST ได้ — เปลี่ยนบทบาท Vigil จาก "ผู้ส่ง" เป็น "ผู้ให้บริการ API ที่ CIB มาดึง" รูปแบบเดียวกับที่ออกแบบไว้แล้วสำหรับฝั่งตรงข้าม (เรา pull จาก HCP) ใน docs/superpowers/specs/2026-06-23-hcp-pull-integration-design.md: auth แบบ AK/SK HMAC-SHA256 (X-Ca-Key/Timestamp/Nonce/Signature), cursor + margin กัน record มาช้า, source_ref unique index กัน insert ซ้ำ — สลับบทบาท client/server จากสเปกเดิมได้เกือบทั้งหมด ข้อดี: buffering กลายเป็นคุณสมบัติในตัว (CIB ขาดการเชื่อมต่อแค่ไหน ก็ poll cursor ไล่ตามทีหลังได้เอง ไม่ต้องพึ่ง spool/retry ของเราเลย) ข้อควรระวัง: ถ้า CIB เป็นฝ่าย poll เรา ต้องมี inbound reachability เข้า Edge — uplink ที่ 2 จาก Phase 5 แก้ปัญหาแค่ ทาง outbound เท่านั้น ต้องออกแบบทาง inbound แยก (เช่นผ่าน Cloudflare Tunnel เดิมที่เปิดอยู่แล้ว)

Rollback: ไม่ตัด push-emulation (Phase 2–5) ทิ้ง — เดินคู่กันได้จนกว่าฝั่ง CIB ย้ายมาใช้ pull API เต็มรูปแบบ
7

Face — แยกเฟส ไม่ผูกกับแผนนี้

ทีหลัง คนละปลายทาง

หลักฐานทั้งหมดในเอกสารนี้เป็น ANPR เท่านั้น ฟีด Face ไปที่ HCP (202.124.201.105) คนละปลายทางจาก CIB ANPR (.106) และมี dedup asymmetry อยู่แล้ว (กล้อง push face ให้ HCP โดยตรง + push ให้ Vigil เองผ่าน /face-push/:token พร้อมกัน — ตาม HCP spec เดิม) ห้ามเอาแผนนี้ไปพันกับ Face โดยไม่แยกวิเคราะห์ก่อน

ข้อจำกัดที่ไม่ใช่เรื่องเทคนิค

DPA นี่คือการเปลี่ยนตัวผู้ส่งข้อมูลป้ายทะเบียนให้หน่วยงานรัฐ จากกล้อง (อุปกรณ์) มาเป็น Vigil (ระบบของบริษัท) — v_license_plates_public ที่มีอยู่แล้วถูก mark ไว้ว่า PDPA-gated/ต้องมี DPA เอกสารนี้ต้องมีข้อสรุปด้าน "สัญญา/ข้อตกลงทางกฎหมาย" คู่กับข้อสรุปด้าน เทคนิค ก่อนจะ cutover จริงใน Phase 2
Feed ที่ใช้งานจริงของภาครัฐ กล้องตัวที่ตรวจสอบมี upload สำเร็จแล้ว 718,458+ ครั้ง ให้ CIB ทุก phase ที่แตะ slot 1 ของกล้อง ต้องมี rollback ที่ทดสอบ/เข้าใจแล้วก่อนลงมือเสมอ Phase 1 ต้องไม่แตะ slot 1 เลยตลอดทั้ง phase
