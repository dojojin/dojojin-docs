## 🟡 งานที่ต้องทำ — เรียงตามความเร่ง

### 1. แก้ query สาย appearances 🔴 กระทบผู้ใช้ตอนนี้

> ✅ **ปิดแล้ว 2026-08-05 — แต่แก้คนละทางกับที่เสนอไว้ข้างล่าง อ่านตรงนี้ก่อน**
> `e42ff68` *perf(appearances): cap the broad-search count at 10,000*
> **"ตัด JOIN ออกจาก query นับ" ทดลองแล้วตกไป** — commit message ระบุเหตุผลไว้:
> ทางไม่มี JOIN วัดได้ >150 วินาที และ `detected_at` กับ `event_time` ไม่ตรงกัน
> **6.6% ของแถว** จึงใช้ `detected_at` ตัดช่วงเวลาแทนไม่ได้
> ที่ทำจริง: คง `JOIN events` ไว้ แล้วครอบ subquery นับด้วย `LIMIT APP_COUNT_CAP`
> (env, default 10000) → ตอบ **"10,000+"** พร้อม header `X-Total-Capped: 1`
> (`src/routes/appearances.js:479`) แทนที่จะจ่ายค่า full scan เพื่อเลขที่ไม่มีใครอ่านครบ
> — คลาสเดียวกับ decision #264 ที่ `/api/events` ใช้ทีหลัง
> ส่วน `_app_stats_filtered` แก้ตามข้อเสนอจริง (ดึงเฉพาะ 4 คีย์ `raw_json->>` แทนทั้งก้อน);
> ตัว temp table เองมีมาตั้งแต่ `1b025eb` (2026-07-20) ก่อนแผนนี้
>
> ⚠️ **เกณฑ์เสร็จข้างล่าง (`search < 3s`) วัดกับของที่ ship ไม่ได้ตรง ๆ** — ตัวเลขที่ได้
> เป็นยอดที่ถูก cap ไม่ใช่ยอดจริง เกณฑ์เดิมสมมติว่ายังนับครบทุกแถว


> **หาต้นตอเจอแล้ว 2026-08-04 — ไม่ใช่เรื่อง index อย่างที่เขียนไว้ตอนแรก**

**ทางที่ตัน (บันทึกไว้จะได้ไม่เดินซ้ำ):**
- `EXPLAIN` ของ query หน้าเพจ = **1.25 ms** · query นับ = 998 ms (ตอน cache อุ่น) → ไม่ใช่ตรงนี้
- `LIMIT $1` แบบพารามิเตอร์ vs เขียนตรง ๆ → เร็วเท่ากันทั้งคู่ (2-24 ms) ไม่ใช่ generic plan
- pool ไม่ตัน (api-server ใช้ 5 จาก max 15) · `shared_buffers` 4GB ไม่ได้เล็ก

**วิธีที่ทำให้เจอ:**
1. `%{time_starttransfer}` ของ curl = 17.8 วิ แต่เวลาส่งข้อมูล ~0 → ช้าที่ฝั่ง server
2. อ่าน `/proc/<pid>/stat` ก่อน-หลัง → **CPU ของ api-server แค่ 0.44 วิ ตลอด 62 วิ** → ไม่ได้คำนวณ นั่งรอ
3. `limit=1` / `50` / `200` ช้าเท่ากันหมด (18.9 / 19.4 / 20.4 วิ) → ต้นทุนคงที่ ไม่ขึ้นกับจำนวนแถว
4. poll `pg_stat_activity` ทุก 120 ms ระหว่างยิงจริง → **จับได้**

```
x213  api-server | active | IO:DataFileRead | SELECT COUNT(*) FROM appearances a JOIN events e ...
x119  api-server | active | IO:DataFileRead | CREATE TEMP TABLE _app_stats_filtered ...
```

**ต้นตอ: `JOIN events` ในการนับ ที่ไม่ได้กรองอะไรเลย**

```sql
SELECT COUNT(*) FROM appearances a JOIN events e ON e.id = a.event_id   -- ไม่มี WHERE
```

| | ผลลัพธ์ | เวลา |
|---|---|---|
| `COUNT(*) FROM appearances` | 662,489 | **27 ms** |
| `COUNT(*) ... JOIN events` (ที่ใช้อยู่) | 662,489 | 1,462 ms อุ่น / **~18 วิ เย็น** |
| ต่าง | **0 แถว** · appearance ที่ไม่มี event = **0** | |

อ่านดิสก์ **41,797 block ≈ 326 MB ต่อคำขอ** (`IO:DataFileRead`) — ตอนเขียนโค้ดวัดได้ 0.38 วิ
เพราะตอนนั้นมี 295k appearances ยังอยู่ใน cache; พอโตเป็น 662k + events 3M/เดือน ก็ทะลุ

**ทางแก้:** ถ้าเงื่อนไขไม่ได้อ้างถึง `e.*` และไม่มี site scope → **ตัด join ออกจาก query นับ**
· ทำเหมือนกันที่ `_app_stats_filtered` ของ `/api/appearances/stats`
· เช็ค `/api/faces` (3.3s) และ `/api/health/details` (5.1s) ว่ารูปแบบเดียวกันไหม

**ไม่ต้องเติม index** — index ไม่ช่วย query ที่ต้องนับทุกแถวอยู่แล้ว
**ลบงานที่ไม่จำเป็นออก ดีกว่าเพิ่ม index มาช่วยงานที่ไม่ควรมี**

- **เกณฑ์เสร็จ:** `search` < 3s และ `stats` < 1s · วัดด้วย `scripts/perf-baseline.sh` รัน 2 รอบ เทียบรอบที่ 2
- **ต้องมีเทสต์** ที่รันทั้ง 2 แบบเทียบตัวเลขจริง ไม่ใช่เชื่อว่า FK รับประกัน
  (ตอนนี้ orphan = 0 แต่ต้องมีอะไรจับถ้าวันหนึ่งไม่ใช่)

### 4. partial index ให้ query ภาพ NVR 🟢 เล็ก คุ้ม

> ✅ **ปิดแล้ว 2026-09-06 — แต่ไม่ได้สร้าง partial index ตามที่เสนอ**
